# LockWatch — разбор блокировок для NAV 2018

Инструмент для Microsoft Dynamics NAV. Отвечает на три вопроса: **какие таблицы и ключи
ждут блокировок и на сколько**, **кто пострадал**, и — при выданном праве — **кто кого
блокирует прямо сейчас**. Разработка на **NAV 2018** (платформа 11.x), целевая среда —
тот же NAV 2018 в изолированном контуре. Родня по крови — LineProfiler: тот же стенд, тот
же способ доставки на объект, тот же стиль объектов и прогонов.

Проект начат 31.08.2026. Кода ещё нет. Всё, что уже установлено **измерением**, лежит в
[docs/FINDINGS.md](docs/FINDINGS.md); что делать первым — в [docs/NEXT.md](docs/NEXT.md).
Читать оба ДО первой строки кода: половина очевидных решений там уже опровергнута
опытом, и повторять их заново дорого.

## Репозиторий считаем ПУБЛИЧНЫМ, пока не решено иначе

По образцу LineProfiler, и по той же причине: он служит материалом для согласования
установки службой безопасности. Значит:

- **Никаких упоминаний конкретной установки**: имён баз данных, названий компаний и их
  систем, номеров и имён доработанных объектов заказчика, номеров задач трекера. Нужен
  пример объекта — брать штатный NAV (`Codeunit 80 Sales-Post`, `Table 37 Sales Line`).
- **Никаких чужих двоичных файлов.**
- **Никаких следов ИИ** ни в коде, ни в комментариях, ни в сообщениях коммитов: ни имён
  ассистентов, ни «generated by», ни атрибуции. Комментарии пишутся как заметки разработчика.
- Секреты и пароли — только вне репозитория.

Имя базы стенда берётся из переменной окружения `LW_DATABASE` (её нет — брать у самой
службы, см. ниже). Захардкоженных имён и номеров в коде быть не должно.

## Платформа (строго)

Только C/SIDE и язык **C/AL**. Никакого AL, никаких расширений AppSource, никакого BC13+.
Типы объектов — только те, что NAV 2018 поддерживает: Table, Page, Report, Codeunit,
XMLport, Query, MenuSuite. Компиляция в порядке зависимостей: Table → Codeunit → Report → Page.

Если понадобится свой компонент .NET — только .NET Framework, компилятор
`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`, он дорослиновский и понимает
только C# 5: без интерполяции строк, без `?.`, без `nameof`. Но **цель — обойтись без
сборки в `Add-ins` вовсе**: это снимает четыре строки из семи в таблице прав.

## Что уже решено — и почему именно так

Решения приняты по итогам разведки на живом стенде (16 агентов, 30.08.2026), и каждое
опирается на замер, а не на рассуждение. Улики — в [docs/FINDINGS.md](docs/FINDINGS.md).

- **Слоёв два, и накопительный — не сторож, а итог.** `sys.dm_os_waiting_tasks`
  дорожает по числу ЖДУЩИХ ЗАДАЧ (из C/AL: 0,12 мс при нуле, 2,08 при шестидесяти,
  **11,95 при двухстах**), то есть ровно тогда, когда сервер уже стоит. Основа —
  `sys.dm_db_index_operational_stats` (0,6 мс на всю базу, цена не зависит от обстановки),
  но как ИТОГ и проверка охвата, а не как сторож: счётчики прирастают только в момент
  КОНЦА ожидания, поэтому триггер по ним опаздывал бы на весь эпизод. Очередь
  опрашивается прямо — 12 мс в шторм это доли процента ядра, беречь надо NAV-половину
  прохода (FINDINGS, раздел 12).
- **`sys.dm_tran_locks` в цикле не трогать никогда** — 45,6 мс при 60 тысячах блокировок,
  и отбор в `WHERE` не помогает вовсе.
- **Штатная `Table 2000000154` — не основа, а разбор одного случая по кнопке.** 2,8 мс
  при двенадцати блокировках и 157,5 мс с ответом в 30 001 строку при тридцати тысячах;
  провайдер материализует всё, отбор его не спасает.
- **Имя пользователя NAV не обещать до ответа заказчика.** Штатная таблица отдаёт его
  только при `EnableDeadlockMonitoring=true`, а это правка конфига, перезапуск экземпляра,
  ОБА права SQL и постоянная серверная сессия XE. Без этого инструмент честно называет
  ОПЕРАЦИЮ, а не человека.
- **Правил разбора имени два, а не одно**: у таблицы номер ключа NAV — суффикс имени
  индекса, у SIFT-представления — число после `$VSIFT$` (индекс у всех зовётся `VSIFTIDX`
  и номера не несёт). Одно правило теряет самый частый случай блокировок NAV молча.
- **Фон — своя самоперевзводящаяся задача `TASKSCHEDULER`**, не Job Queue: очередь на
  целевом контуре доработана заказчиком, и вешаться в неё — значит зависеть от чужих правок.
- **Период опроса заметно меньше 10 секунд**: предел ожидания блокировки у NAV —
  10 000 мс, и эпизод целиком укладывается в это окно.

## Кодировки — здесь ломается чаще всего

| Что | Как |
|-----|-----|
| Объекты C/SIDE (`*.txt`) | UTF-8 **без BOM**, переводы строк **CRLF** |
| `.ps1` для Windows PowerShell 5.1 | UTF-8 **С BOM**, CRLF |
| `.ps1` под pwsh 7 (`#requires -Version 7`) | UTF-8 без BOM, CRLF |
| Шаблоны объектов, едущие телом письма | **только латиница** |
| Импорт в C/SIDE | cp866; cp1251 и UTF-8 ломают кириллицу |

Windows PowerShell 5.1 читает файл **без BOM как ANSI** и ломается на кириллице в
кавычках: часть команд печатается вместо выполнения. Это не теория, ловилось многократно.

**`sed -i` из git bash снимает с файла CR — весь и молча.** Правку объекта делать
`[regex]::Replace` над `ReadAllText` с записью через `UTF8Encoding($false)`. Проверять
после любой пакетной правки — счётом байтов 13 и 10, а не глазами.

Скрипты правок писать **файлом**, а не heredoc: `python - <<'PY'` в этой оболочке теряет
обратные косые, замена молча находит ноль совпадений, и правка исчезает бесследно.

## Стенд

Стендов **два**, оба на `localhost`, и они независимы.

**Первый** — экземпляр службы NAV `DynamicsNAV110` с базой на схеме целевой установки без
объёмов (102 345 строк). На нём снята разведка 30.08.2026.

**Второй, и он важнее** — полный набор объектов целевой установки на своей NAV 2018:
3 055 таблиц, 5 984 индекса, 248 представлений `VSIFT`. На нём меряется всё, что зависит
от боевой схемы: разбор имён, обратный поиск по хэшу ключа, охват ключей. Служба этого
экземпляра обычно остановлена, и для замеров по SQL она не нужна.

**Имена баз, экземпляров и компаний в репозиторий не пишутся.** Инструмент берёт имя базы
из переменной окружения `LW_DATABASE`, имя экземпляра — из `LW_INSTANCE`. Конкретные
значения обоих стендов, номера и имена объектов заказчика — в `local/stand.md`, который
лежит вне git. Имя базы первого стенда можно взять и у самой службы:

```powershell
([xml](Get-Content 'C:\Program Files\Microsoft Dynamics NAV\110\Service\CustomSettings.config')).appSettings.add |
  Where-Object { $_.key -in 'DatabaseServer','DatabaseName','ServerInstance' } |
  ForEach-Object { "$($_.key) = $($_.value)" }
```

Модуль NAV (`Invoke-NAVCodeunit`, `Get-NAVServerSession`, `NavAdminTool.ps1`) грузится
**только в Windows PowerShell 5.1** — pwsh 7 падает на `RealProxy`. Скрипты репозитория
идут под pwsh 7.

`TEMPORARYPATH` у NAV — не temp учётной записи службы, а профиль экземпляра:
`…\Server\MicrosoftDynamicsNavServer$<экземпляр>\users\default\<домен>\<пользователь>\TEMP`.
В пути есть знак доллара: гнать его строкой через bash в `powershell -Command` нельзя,
доллар съедается и `Test-Path` врёт. Такие пути читать инструментом PowerShell напрямую.

**Правку настройки мимо NAV сервер не видит**: при работающей службе строка настройки
лежит в кэше, и `UPDATE` прямо в SQL до сессии не доходит. Лечится перезапуском экземпляра.

## Как проверять — прогоном, а не рассуждением

Прогонов пока нет: их надо завести вместе с первым объектом, по образцу LineProfiler.
Требования к ним те же:

1. Обкатка обязана **судить сама**: «пройдено N из M» первой строкой, и первая проверка —
   что результат вообще не пуст, иначе остальные проходят вхолостую.
2. Каждая проверка обязана быть **непустой**: сломать нарочно то место, которое она
   меряет, и убедиться, что она краснеет. Число «на прежнем коде даёт X» записывать рядом.
3. Всё, что можно проверить **без базы**, проверяется без базы: разбор имени SQL в таблицу
   и ключ NAV, счёт дельт, отсев сброса счётчиков — это чистые функции над данными.
4. Перед отправкой на объект — собрать пакет и поставить **из него**, а не из рабочей копии.

## Стиль работы

- Уточняющие вопросы задавать **по одному**.
- **Числу в коде верить нельзя**: у каждой величины имя и довод — функция без параметров
  рядом с комментарием, объясняющим число. В настройке живёт только то, что зависит от
  СРЕДЫ; смысловые пределы — функцией в коде. Номер объекта — не число, а имя:
  `CODEUNIT::"…"`, `DATABASE::"…"`.
- Рукописная строка в объекте C/AL — не длиннее 130 знаков. На скрипты правило не
  распространяется.
- **Выгрузку и пакет собирать только по просьбе.** Правка, проверка прогоном, коммит и
  push — обычная работа и делаются сами.
- После каждого коммита — `git push`; локальные коммиты не накапливать.
