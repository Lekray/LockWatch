# С чего начинать

Порядок здесь не случайный: первые четыре пункта стоят часы, а решают, каким будет
инструмент. Писать код до них — значит переписывать его после.

## Что решено и что ещё блокирует проектирование

**Диапазон номеров объектов — `110230` и выше** (решено 07.09.2026). Остаётся проверить
столкновение **по имени**: на стенде уже есть нештатные объекты с именем «Database Lock».

**Вопрос заказчику остался один: готовы ли включить `EnableDeadlockMonitoring`.** Это
единственный способ получить имена ЛЮДЕЙ от самой платформы, и цена его — правка
`CustomSettings.config`, перезапуск экземпляра, оба права SQL, постоянная серверная сессия
Extended Events, переживающая снятие инструмента, и дополнительный запрос к SQL на каждом
старте транзакции в каждой сессии. Подробности и улики — [FINDINGS.md](FINDINGS.md),
раздел 2.

От ответа зависит, обещаем мы имена **от платформы** или нет. **Пока ответа нет — не
обещать.** Свой путь к имени, не требующий ни прав, ни перезапуска, описан в
[JOURNAL.md](JOURNAL.md), раздел 7.2, и уже проверен на стенде.

## Пятиминутная проверка на целевом контуре

Стоит пяти минут, экономит две недели. Прогнать **от имени учётной записи службы**:

```sql
SELECT HAS_PERMS_BY_NAME(null, null, 'VIEW SERVER STATE'),
       HAS_PERMS_BY_NAME(null, null, 'ALTER ANY EVENT SESSION');
SELECT COUNT(*) FROM sys.dm_db_index_operational_stats(DB_ID(), NULL, NULL, NULL);
SELECT COUNT(*) FROM sys.dm_os_waiting_tasks;
```

И снять базовое число строк в `dm_os_waiting_tasks` **в час пик**. Если их там сотни,
фоновый опрос очереди не годится в принципе, и остаётся только накопительный слой.

## Два дешёвых опыта на стенде

Оба про ETW и оба решают, можно ли назвать человека **без единого права SQL**
([FINDINGS.md](FINDINGS.md), раздел 7).

1. **Приходит ли `FuncFail` на отказ по блокировке.** Поднять приёмник, устроить ту же
   блокировку двух сеансов NAV и посмотреть, что прилетает жертве на пределе 10 000 мс.
   Ожидание: `userName`, `objectType`, `objectId`, `functionName`, `failureMessage` с
   именем таблицы.
2. **Идут ли SQL- и транзакционные события при выключенном `EnableFullALFunctionTracing`.**
   Если для них нужен тот же флаг — дорога через ETW теряет смысл: цена ровно та, от
   которой мы бежим.

Устройство опыта уже отработано: временный кодюнит берёт `LOCKTABLE` на свою таблицу и
держит `SLEEP`, вторая сессия встаёт в очередь; съём идёт с третьего соединения. Обе
сессии запускаются `Invoke-NAVCodeunit` из Windows PowerShell 5.1.

## Устройство, каким оно вырисовывается

Три уровня, каждый работает сам по себе и включается отдельно. Это не этапы разработки, а
**уровни прав**: заказчик может остановиться на любом.

**Уровень 0 — без единого нового права.** Несущий слой журнала:
`sys.dm_db_index_operational_stats` раз в N секунд, в базу пишутся только приросты.
Отвечает: какая таблица, какой ключ, сколько раз ждали и сколько миллисекунд, сколько
было эскалаций. Видит SIFT. Не отвечает: кто и когда именно. Плюс именованная половина
жертвы — обёртка `[TryFunction]` вокруг подозрительной операции: жертва знает свою
учётку, объект и функцию сама.

**Уровень 1 — `VIEW SERVER STATE`** (на стенде учётке службы уже выдан). Живая цепочка
«кто кого»: `dm_os_waiting_tasks` + `dm_exec_sessions`, ждущий оператор жертвы, последний
оператор спящего виновника через `most_recent_sql_handle`, номер объекта NAV из псевдонима
в тексте запроса. Взаимоблокировки даром из `system_health`. **Опрашивать прямо, без
триггера**: накопительные счётчики прирастают лишь в момент конца ожидания, поэтому
триггер по ним опаздывает на весь эпизод (раздел 12). Цена DMV растёт с длиной очереди
(12 мс при 200 ждущих), но это доли процента ядра; беречь надо NAV-половину прохода. Журнал
эпизодов, который на этом уровне ведётся, расписан в [JOURNAL.md](JOURNAL.md).

**Уровень 2 — конфиг и перезапуск.** Имена людей от платформы, `Table 2000000154`, только
по кнопке и на один разбираемый случай (157 мс в шторм). По умолчанию выключено.

### Что заложить в устройство с самого начала

- **Сторож, без которого экран врёт.** Проверять права тем же запросом, каким проверяет
  платформа, плюс наличие сессии `<База>_deadlock_monitor`, плюс перекрёстную проверку
  «в `dm_os_waiting_tasks` есть ожидание `LCK_*`, а `2000000154` пуста» = карта мертва.
  Пока сторож не зелёный — страница пишет «имена недоступны, причина такая-то», а не
  показывает пустой список.
- **Обратная связь на разрежение, а не на учащение**: при непустом пульсе период
  увеличивать; потолок строк за проход и миллисекунд за проход с видимой отметкой
  «усечено» — иначе в шторм журнал сам себя разгоняет.
- **Эпизод одной строкой**, которая обновляется, а не плодится снимками.
- **Срок хранения и порционная чистка** — объявленные, с автоматическим исполнением.
- **Колонки AL подписать честно**: «где виновник исполняется СЕЙЧАС», а не «где взял
  блокировку».
- **Корреляцию никогда не подавать как ответ на „кто“.** Сводка с журналом заданий —
  фактбоксом «в это окно шли задания …», отдельной строкой, никогда не «виновник».

## Чего в замысле пока нет

Цена NAV-половины прохода **измерена** 07.09.2026 и лежит в [FINDINGS.md](FINDINGS.md),
раздел 13: 408 мс на 500 строк при потолке 1000. Обещаний, не подкреплённых замером, в
замысле больше не осталось.

Следующее по порядку — **съём с SQL**: опрос очереди, разматывание цепочки по уже
прочитанным строкам, ведение эпизода журналом (`Codeunit 110232`, готов и обмерен) и своя
самоперевзводящаяся задача `TASKSCHEDULER`. Мерить придётся ещё раз, уже целым проходом:
съём и запись меряны порознь, а вместе они делят одно соединение.
