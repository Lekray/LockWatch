# Что установлено измерением

Разведка на живом стенде NAV 2018, 30.08.2026. Всё ниже — замер или чтение кода
платформы, а не рассуждение; где это вывод, так и написано. Половина очевидных решений
здесь уже опровергнута опытом — читать до первой строки кода.

Стенд: SQL Server 2022 Developer, экземпляр службы NAV 11.x, база — копия схемы целевой
установки (102 345 строк во всей базе, то есть схема боевая, объёмов нет).

---

## 1. Личность: со стороны SQL пользователя NAV не назвать

**Все сессии службы неотличимы.** 66 из 67 пользовательских сессий SQL идут под
`NT AUTHORITY\NETWORK SERVICE`, `program_name` у всех «Microsoft Dynamics NAV Server»,
`context_info` пуст (`0x`), `host_name` — имя сервера, `host_process_id` один и тот же у
всех. Различаются только номера spid.

**Настройкой это не чинится.** Ключа вида `EnableSqlConnectionTagging` в NAV 2018 нет ни в
`CustomSettings.config`, ни в бинарях платформы.

**И привязка к spid нестабильна по устройству**: одна сессия NAV держит десятки spid из
пула — 81 на одного клиента, 3 после его выхода.

**Виртуальная `Table 2000000009 Session` не мост**: на NST она отдаёт только СВОЮ строку
(при двух живых сессиях `COUNT=1`), а её `Connection ID` равен номеру сеанса NAV, не spid.

Вывод: **имя обязана называть сторона NAV.** SQL его не знает и знать не может.

## 2. Штатная `Table 2000000154 «Database Locks»` — и почему она пуста

Единственная штатная таблица про блокировки; единственная страница над ней — `Page 9511`,
без единого действия и без отбора. Девять полей: `Transaction Id`, `SQL Object Name`,
`SQL Resource Type`, `SQL Request Mode`, `SQL Request Status`, `User Name`,
`AL Object Type`, `AL Object Name`, `AL Method Scope`.

**Цепочки «кто кого» она не даёт принципиально.** SQL под ней (константа
`SelectDatabaseLocksCommand`) выбирает только `request_owner_id`, имя объекта, тип
ресурса, режим и статус запроса. Ни `request_session_id`, ни `blocking_session_id`, ни
`resource_description` там нет вовсе, а `request_mode LIKE 'I%'` и `Sch-%` отброшены.

**Имя пользователя и объект AL платформа подставляет сама**, по своей карте
«транзакция → сессия» (`DatabaseLocksDataProvider.GetTransactionSessionMapForTenant`).

**На живой блокировке двух сессий NAV таблица вернула НОЛЬ строк** — и стороннему
наблюдателю, и самому держателю, читавшему её изнутри своей же открытой транзакции.
Чтение проходит успешно и быстро (85 мс), набор пуст.

Причина доведена до строки кода. `AddDatabaseLockToRecordList` выбрасывает строку, если
`transaction_id` не найден в карте. Карту наполняет `CurrentTransactionId` каждой сессии,
а он заполняется в `NavSqlConnection.BeginTransaction` только при взведённом
`ConnectionPool.TransactionHistory`. `EnableTransactionHistory()` зовётся ровно один раз —
в `NavEnvironment.SetupDeadlockAnalyzer`, на одноразовом обработчике `DatabaseFirstAccess`,
и только при `EnableDeadlockMonitoring=true`. На стенде — `false`.

Тот же запрос платформы, выполненный руками и **от имени учётки службы**
(`EXECUTE AS LOGIN`), честно вернул обе ожидаемые строки. Дело не в правах и не в
лицензии — строки выбрасывает сам провайдер.

### Чем платят за включение

| Что требуется | Подробность |
|---|---|
| `EnableDeadlockMonitoring=true` | правка `CustomSettings.config` |
| Перезапуск экземпляра | взвод висит на `DatabaseFirstAccess`, права снимаются один раз |
| **Оба** права SQL | `VIEW SERVER STATE` И `ALTER ANY EVENT SESSION`; проверяются запросом `HAS_PERMS_BY_NAME` один раз при первом обращении к БД |
| Постоянная серверная сессия XE | `<База>_deadlock_monitor`, `STARTUP_STATE=ON`, **переживает снятие инструмента** — убирает её только обратное выключение ключа |
| Надбавка на каждой транзакции | `SELECT TOP 1 transaction_id FROM sys.dm_tran_session_transactions WHERE session_id = @@spid` на КАЖДОМ старте транзакции в КАЖДОЙ сессии (0,062 мс против 0,083 мс у `SELECT 1` на 500 прогонах — но на выносном сервере это сетевой круг) |

**Отказ невидим.** Не выдали право — платформа пишет одну строку трассировки уровня
Warning, и таблица ведёт себя в точности как при отсутствии блокировок. Экран будет пуст
и на здоровой системе, и на сломанной.

### Три скрытых отбора

1. Компания владельца блокировки обязана совпасть с компанией **читающей** сессии
   (исключение — таблицы с `DataPerCompany=No`). Один наблюдатель не увидит чужой компании.
2. Intent- и схемные блокировки отброшены — а на живом сервере это большинство строк.
3. Всё, что держит не сессия NAV этого тенанта с текущим соединением, не появится
   никогда: чужой экземпляр службы, внешнее подключение, собственная обёртка ADO.NET.

### И колонки AL отвечают не на тот вопрос

`AL Object Type / Id / Method Scope` берутся из **живого стека виновника в момент
чтения** (`CurrentMethodScope.StackTrace?.LastOrDefault()`) — самый глубокий кадр СЕЙЧАС,
а не тот, что взял блокировку. Длинная проводка держит блокировку и уходит через десятки
кодюнитов: два соседних опроса одного эпизода назовут разные объекты.

### Цена чтения

2,8 мс при 12 блокировках; **157,5 мс и 30 001 строка** при 30 тысячах. Провайдер
`EagerVirtual`: любое чтение, даже `FINDFIRST` с отбором, материализует ВСЕ блокировки
экземпляра и обходит ВСЕ живые сессии. То есть дороже всего он именно в шторм.

## 3. Сторона SQL: работает уже сегодня

`VIEW SERVER STATE` учётной записи службы **уже выдан явным GRANT**, sysadmin у неё при
этом нет (проверено `EXECUTE AS`).

**Цепочка «кто кого» снимается одним запросом за 0,64 мс** (`sys.dm_os_waiting_tasks` +
`sys.dm_exec_sessions`): жертва, виновник, тип и режим ожидания, миллисекунды ожидания,
ресурс с `hobt_id`, состояние виновника и номера транзакций обеих сторон. Живой пример со
стенда: держатель — сеанс NAV 270, spid 75, транзакция 988137, `KEY U GRANT`; жертва —
сеанс 272, spid 98, транзакция 988924, `KEY U WAIT`, `LCK_M_U`.

**Виновник СПИТ.** `status=sleeping`, строки в `dm_exec_requests` у него нет вовсе — его
последний оператор достаётся только через `dm_exec_connections.most_recent_sql_handle`.
У жертвы, наоборот, строка есть, и её точный ждущий оператор берётся по
`statement_start_offset/end_offset`.

**`resource_description` уже несёт `hobt_id`** — заходить в дорогую `dm_tran_locks` ради
ресурса не нужно.

**Мост «транзакция → сессия» строить по ДВУМ DMV.** Сторона внутри транзакции резолвится
через `dm_tran_session_transactions`; автокоммитный оператор — нет: его `transaction_id`
есть в `dm_exec_requests`, а в `dm_tran_session_transactions` его нет вовсе. У NAV пишущая
сторона всегда в транзакции, а вот жертва-читатель — не всегда.

**Предел ожидания блокировки у NAV — 10 000 мс.** Замерено дважды: жертва умирала на
10 099 и 10 120 мс со штатным текстом «запись заблокирована другим пользователем». После
отказа она исчезает из `dm_os_waiting_tasks` мгновенно.

**Подарок: номер объекта NAV лежит прямо в тексте запроса.** Платформа даёт таблице
псевдоним, равный номеру объекта: `SELECT TOP (1) "110201"."timestamp","110201"."Entry No_"`.

## 4. Цена наблюдения — главная поправка

Первоначальное «цена плоская по числу блокировок» **измерено не по той оси**.
`sys.dm_os_waiting_tasks` дорожает по числу **ждущих задач**, а разведка меняла число
блокировок, держа одну-две ждущих.

Из C/AL, тем самым транспортом (DotNet `SqlClient`), 500 прогонов на прогретом плане:

| Ждущих задач | Пульс | Полная цепочка |
|---|---|---|
| 0 | 0,12 мс | 0,29 мс |
| 60 | 2,08 мс | 5,95 мс |
| 200 | **11,95 мс** | 21,60 мс |

Со стороны SQL: 36 ждущих → 0,106 мс; 236 ждущих → **7,87 мс** (рост в 74 раза), при том
что блокировок было всего 609. **Отбор не спасает**: тот же запрос с заведомо пустым
условием — 7,83 мс, голый `COUNT(*)` — 7,88 мс. Дешёвого сторожа на этом DMV нет.

Для контроля: чтение 300 строк из `sys.objects` стоило 5,3 мс и от шторма не зависело —
дорожает не маршалинг строк в C/AL, а само перечисление ждущих задач.

### Способы наблюдения, от дешёвого к дорогому

| Способ | Цена | Что даёт | Права |
|---|---|---|---|
| `sys.dm_db_index_operational_stats(DB_ID(),…)` | **0,46–0,6 мс** на всю базу, 220 строк | накопительно по таблице и ключу: сколько раз и сколько мс ждали, эскалации. **Видит SIFT** | **никаких сверх имеющихся** — читается при `VIEW SERVER STATE = 0` |
| `sys.dm_os_wait_stats` по `LCK_*` | 0,44 мс | итог по экземпляру, масштаб беды | даром |
| `system_health` ring buffer | 37 мс за чтение | `xml_deadlock_report` целиком, без настройки. `blocked_process_report` там **нет** | `VIEW SERVER STATE` |
| `dm_os_waiting_tasks` + `dm_exec_sessions` | 0,1 мс праздно, **12 мс в шторм** | «кто кого», ресурс, ждущий оператор | `VIEW SERVER STATE` |
| `sys.dm_tran_locks` | 3,1 мс праздно, 45,6 мс при 60 тыс. | в цикл **не ставить**, отбор не помогает | `VIEW SERVER STATE` |
| `blocked_process_report` | дёшев по устройству | см. ниже | правка настройки СЕРВЕРА (sysadmin) + своя сессия XE |
| `lock_acquired` / `lock_released` | событие на каждую блокировку | **не брать** | — |

### `blocked_process_report`: разведка ошиблась дважды

Дешевизна **подтвердилась и объяснима**: отчёт поднимает уже работающая фоновая задача
`LOCK MONITOR`, расход пропорционален числу ждущих дольше порога, а не числу блокировок.
Замерено: на блокировку длиной 17 с при пороге 5 с пришло ровно 3 отчёта.

Но **готовых `object_id`/`index_id` он не даёт**. Они верны только для `OBJECT`-блокировки;
на обычной построчной `KEY`-блокировке — ради которой всё и затевается — там мусор:
`rep_object_id=16992` при настоящем `1461580245`. Настоящий ресурс лежит только в XML.
И в этом же XML едет **полный текст операторов обеих сторон со значениями** — для службы
безопасности это выгрузка данных, а не структура.

## 5. Разбор имени: два правила, а не одно

**Имя таблицы NAV** из имени SQL: `[Компания]$[Имя таблицы]`, где `. / \ "` заменены
подчёркиванием, а у таблиц с `DataPerCompany=No` префикса компании нет вовсе. Обратная
карта покрывает 2526 из 2545 пользовательских таблиц; непокрытые 19 — платформенные
`$ndo$*`. Ни одна таблица NAV не теряется.

**Номер ключа NAV** — суффикс имени индекса после последнего `$`. Тонкости: у кластерного
индекса имя полное (`…$0`), у вторичных просто `$1`, `$5`, `$13`; номера **не сплошные**
(у выключенных ключей индекса в SQL нет); `index_id` и номер ключа NAV — разные вещи.

**Карту строить один раз (28 мс) и держать в памяти.** Поштучное разрешение стоит 19,1 мс
за блокировку — в цикле недопустимо.

### SIFT ломает оба правила, и это самый частый случай

Классическая блокировка NAV садится не на таблицу, а на её **SIFT-представление**.
Проверено опытом на индексированном представлении-агрегате: два сеанса, вставляющие
**РАЗНЫЕ** строки, столкнулись на общей корзине агрегата —
`row_lock_wait_in_ms = 2047` у представления и **ноль** у базовой таблицы.

В базе стенда **308 представлений `VSIFT`** над 154–187 таблицами, имена вида
`<Компания>$<Таблица>$VSIFT$<n>`, и индекс у всех один и тот же — `VSIFTIDX`. Отсюда:

- карта, построенная по `sys.tables`, их не покрывает: `VIEW` — разрешено 4, **не
  разрешено 311**;
- правило «номер ключа из суффикса имени индекса» на них даёт `VSIFTIDX` — цифр нет.

Лечение: в карту класть и `sys.views`; имя разбирать по **последнему** вхождению
`$VSIFT$` — левая часть даёт таблицу, правая номер ключа. Ожидания представления
подкладывать под базовую таблицу, но **отдельной колонкой** «в т.ч. на SIFT-агрегате,
ключ N»: это и есть готовый ответ на «из-за чего» — не конкуренция за строку, а
поддержание агрегата, и лечится `SumIndexFields`, а не индексом.

Строку, чей hobt не разрешился, **никогда не выбрасывать**: показывать сырым именем с
пометкой «не опознано» и считать счётчиком. Молчаливый пропуск — это и есть ложь.

### Две молчаливые ловушки разбора

`OBJECT_NAME` без второго аргумента разрешает имя в базе **вызывающего** и возвращает
правдоподобное ЧУЖОЕ имя — фильтр по `resource_database_id` обязателен. И `OBJECT_NAME`
от `hobt_id` роняет запрос переполнением int: ветвление по `resource_type` обязательно.

## 6. Фоновая работа: только `TASKSCHEDULER`

Единственный механизм, дающий работу без клиента, которая переживает перезапуск службы
(задача лежит строкой в базе, есть владелец-экземпляр и heartbeat, платформа умеет
восстанавливать задачи умершего экземпляра) и имеет обработчик падения — Failure Codeunit.

- **Job Queue** — прикладная обёртка над ним же; на целевом контуре доработана заказчиком,
  вешаться туда — зависеть от чужих правок и делить чужой лимит.
- **`STARTSESSION`** — только разовый запуск и запасной путь, когда `CANCREATETASK` вернул
  `FALSE`: ни отложенного старта, ни обработчика ошибок, ни переживания рестарта.
- **NAS и своя служба Windows** — отпадают: лицензия и правка конфига у первого, прямое
  нарушение обещания «ни служб, ни планировщика» у второй.

Проверено на стенде: задача поднялась (`ClientType=Background`), `SLEEP(2000)` точен
(интервалы 2,006–2,037 с), `DotNet SqlClient` из фоновой сессии работает, задача заняла
ровно один слот планировщика на всё время жизни.

**Два ограничения записать сразу.** Постановка задачи требует `COMMIT` (внутри незакрытой
транзакции она не создастся). `MESSAGE` из фоновой сессии уходит в журнал событий NAV, а
не на экран — фоновому коду нужен свой способ отчитаться.

**И один потолок.** `TooManyRunningTasks()` при 10 незавершённых задачах заставляет
планировщик выйти НЕ ЗАПУСТИВ НИЧЕГО. Долгоживущая задача постоянно держит 1 слот из 10,
делимых с заданиями заказчика: цикл должен быть коротким и перевзводить себя, а не жить
вечно одной задачей.

## 7. ETW: запасная дорога к именам, не требующая прав SQL

Каталог событий провайдера NAV, снятый с этого стенда:

```
id=402 kind=FuncFail  fields=navTenantId,sessionId,userName,objectType,objectId,
                             functionName,failureMessage,serverInstanceName,…
id=11/12 task=6       fields=navTenantId,sessionId,userName,serverInstanceName
id=1..10 kind=Sql*    fields=navTenantId,sessionId,userName,sqlStatement,serverInstanceName
id=403 kind=Statement fields=navTenantId,sessionId,objectType,objectId,functionName,
                             lineNumber,statement,…
```

**Учётка NAV и номер сеанса лежат в каждом событии**, у отказа — ещё объект, функция и
текст ошибки. Прав SQL не нужно вовсе: приёмник сидит внутри процесса службы.

**Идентификатора соединения SQL нет ни в одном событии** — сшить ETW с блокировкой на
стороне SQL нечем. Это самостоятельная дорога, а не мост.

Что из этого следует (вывод, не замер): жертву можно назвать поимённо без единого права
SQL, а виновника — только списком подозреваемых «кто держал открытую транзакцию с записью
в эту таблицу в момент отказа».

**Не проверено вживую, и это две дырки:**

1. приходит ли `FuncFail` на отказ по блокировке;
2. идут ли SQL- и транзакционные события **без** `EnableFullALFunctionTracing` — если для
   них нужен тот же флаг, что для построчного профайлера, цена ровно та, от которой мы
   бежим (событие на каждый оператор C/AL, весь сервер медленнее, плюс перезапуск).

## 8. Номера объектов и прецедент безопасности

`110210–110259` на стенде пусты полностью; `110200–110209` заняты (17 объектов профайлера
и приватные вспомогательные, вперемешку по типам). **Разрешённый лицензией ЗАКАЗЧИКА
диапазон неизвестен**: лицензия стенда внутренняя сборочная и перечня диапазонов не
содержит вовсе. И проверять надо столкновение **по имени тоже** — на стенде уже есть
нештатные объекты с именем «Database Lock».

LineProfiler прошёл согласование не потому, что просил мало, а потому, что каждое
требование объяснил, снабдил командой проверки и колонкой «а если не дадите», и отдал
службе безопасности рычаг: два права SQL объявлены необязательными, съём реальных данных
выключен по умолчанию, имена чужих пользователей не читаются вовсе.

LockWatch делает **два разворота** против этого прецедента: он ПОКАЗЫВАЕТ учётки других
людей и копит журнал ФОНОМ, а не внутри окна «Старт—Стоп». Значит взамен обязан отдать
больше: одно право уровня сервера вместо sysadmin, никакой правки `CustomSettings.config`
и перезапуска, по возможности без сборки .NET в `Add-ins` вовсе, значения данных —
отдельной выключенной галкой, и объявленный срок хранения журнала с автоматической
чисткой, которого у профайлера нет.

## 9. Обратный поиск по хэшу ключа: проверено на схеме целевой установки

Стенд второй, и он важнее первого: полный набор объектов целевой установки на своей
NAV 2018 — **3 055 таблиц, 5 984 индекса, 248 представлений `VSIFT`**. Имя базы — в
`LW_DATABASE`. Замеры 07.09.2026, служба NAV при этом остановлена: всё ниже снимается
одним SQL и работающего экземпляра не требует.

**Хэш ключа обратим.** `resource_description` у `KEY`-блокировки — это хэш значений ключа,
и строка по нему находится запросом `WHERE %%lockres%% = '(…)'`. Проверено насквозь на
настоящей блокировке: сессия взяла `UPDLOCK` на строку штатной `Table 17 «G/L Entry»`,
наблюдатель со стороны увидел `KEY U`, хэш `(92410d4f079d)` и транзакцию 12337914,
разрешил хэш по индексу из `hobt_id` и получил **ровно ту строку**. Цена — 2,3 мс на
4 149 строк, то есть скан индекса.

Это и есть мост из раздела 7.2 [JOURNAL.md](JOURNAL.md): «транзакция виновника → её
блокировки → строка» — не корреляция, а факт, и он работает.

**Хэш считается по КОНКРЕТНОМУ индексу, и ошибка индекса не видна.** Одна и та же строка
даёт `(61a06abd401c)` на кластерном индексе и `(25d1acec8a76)` на вторичном. Поиск по хэшу
вторичного без `INDEX(...)` возвращает **пустой набор и никакой ошибки**. Значит
пропущенное ветвление по индексу выглядит как «строка не найдена» — ровно тот молчаливый
отказ, который дороже всего искать потом.

**Ветвление окупается почти всегда.** У NAV вторичный ключ уникален и несёт поля
кластерного ключа хвостом: из **2 930 вторичных индексов базы 2 903 содержат весь
кластерный ключ**, и только 27 — нет. Блокировка почти на любом индексе таблицы-контекста
разрешается в строку, у которой номер документа на месте; способ не ограничен кластерным.

**`resource_description` приходит добитым пробелами** до ширины столбца DMV. Сравнение
`%%lockres%% = @res` это переживает — SQL игнорирует хвостовые пробелы, — а вот склейка
хэша в текст запроса не переживает. Обрезать при чтении.

**Поправка к цене накопительного слоя.** На этой базе
`sys.dm_db_index_operational_stats` вернула **136 строк за 1,3 мс** против 220 строк за
0,6 мс на первом стенде — при том что таблиц здесь в двенадцать раз больше. DMV отдаёт
строки только по объектам, у которых была активность с последнего перезапуска, поэтому её
размер зависит от НАГРУЗКИ, а не от схемы. Планировать объём журнала по числу таблиц нельзя.

## 10. Что видно по исходникам объектов целевой установки

Выгрузка объектов целевой установки — 13 835 объектов, вне репозитория, путь в
`local/stand.md`. Прочитано 07.09.2026.

**Диапазон `110230` и выше свободен на живом наборе.** Занято `110200–110207` —
семнадцать объектов профайлера; выше и до `110400` пусто. И столкновений **по имени** со
словом «Lock» среди 13 835 объектов нет ни одного: единственный носитель имени
«Database Locks» — штатная `Page 9511`. Предостережение раздела 8 относилось к другому
стенду и на целевую установку не переносится.

**Врезка в чужой код НЕ НУЖНА: есть подписка на события таблицы.** Платформа 11 поднимает
глобальные события таблиц, и целевая установка ими уже вовсю пользуется — 108 подписок на
`OnAfterInsertEvent`, 76 на `OnAfterModifyEvent`, 73 на `OnAfterDeleteEvent`. Синтаксис в
тексте объекта:

```
[EventSubscriber(Table,37,OnAfterModifyEvent)]
LOCAL PROCEDURE OnAfterModify@1(VAR Rec@1000 : Record 37;VAR xRec@1001 : Record 37;RunTrigger@1002 : Boolean);
```

Подписчик исполняется **внутри транзакции пишущего** — ровно то, что нужно записи
контекста ([JOURNAL.md](JOURNAL.md), раздел 7.2): отметка ложится в ту же транзакцию, и
её собственная блокировка становится мостом. Значит путь к имени и номеру, который
казался самым дорогим, **не требует ни одной правки в объектах заказчика**.

**Но номер таблицы в подписке — константа времени компиляции**, и типизированный параметр
`Record <номер>` тоже. Настройкой это не обходится: подписчик на таблицу контекста —
отдельный маленький объект-переходник, свой для каждой установки. В репозитории он живёт
**шаблоном** со штатной таблицей в примере, боевой номер подставляется на месте. Отсюда
правило: список таблиц контекста в настройке отвечает за РАЗБОР, а переходник — за СЪЁМ,
и сторож обязан ругаться, когда в настройке есть таблица, для которой переходника нет.

**SIFT целится не туда, куда казалось.** Из 158 таблиц с `SumIndexFields` клиентских
всего 7 — остальное штатные регистры. SIFT-блокировки будут приходить на штатных
таблицах, а таблицы документов заказчика от них свободны; у самой таблицы контекста
представлений `$VSIFT$` нет вовсе, и ключ у неё одиночный. Для номера документа это
означает разбор без составного ключа.

**Поправка к разделу 6.** Диспетчер очереди заданий (`Codeunit 448`) и стартовый кодюнит
`449` на целевой установке **не тронуты**, они штатные; доработаны только `Table 472` и её
карточка — заказчик добавил свои поля. Значит довод «очередь доработана заказчиком» верен
наполовину: чужих правок сам механизм не несёт. Против очереди остаётся другое — она
общая, с общим лимитом и общим администрированием, и запись задания в ней видна и
редактируема тем, кого мы наблюдаем.
