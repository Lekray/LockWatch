# Что установлено измерением

Разведка на живом стенде NAV 2018, 30.08.2026. Всё ниже — замер или чтение кода
платформы, а не рассуждение; где это вывод, так и написано. Половина очевидных решений
здесь уже опровергнута опытом — читать до первой строки кода.

Стенд: SQL Server 2022 Developer, экземпляр службы NAV 11.x, база — копия схемы целевой
установки (102 345 строк во всей базе, то есть схема боевая, объёмов нет).

---

## 1. Личность: со стороны SQL пользователя NAV не назвать

**Все сессии службы неотличимы.** 66 из 67 пользовательских сессий SQL идут под
`NT AUTHORITY\NETWORK SERVICE`, `program_name` у всех «Microsoft Dynamics NAV Server»,
`context_info` пуст (`0x`), `host_name` — имя сервера, `host_process_id` один и тот же у
всех. Различаются только номера spid.

**Настройкой это не чинится.** Ключа вида `EnableSqlConnectionTagging` в NAV 2018 нет ни в
`CustomSettings.config`, ни в бинарях платформы.

**И привязка к spid нестабильна по устройству**: одна сессия NAV держит десятки spid из
пула — 81 на одного клиента, 3 после его выхода.

**Виртуальная `Table 2000000009 Session` не мост**: на NST она отдаёт только СВОЮ строку
(при двух живых сессиях `COUNT=1`), а её `Connection ID` равен номеру сеанса NAV, не spid.

Вывод: **имя обязана называть сторона NAV.** SQL его не знает и знать не может.

## 2. Штатная `Table 2000000154 «Database Locks»` — и почему она пуста

Единственная штатная таблица про блокировки; единственная страница над ней — `Page 9511`,
без единого действия и без отбора. Девять полей: `Transaction Id`, `SQL Object Name`,
`SQL Resource Type`, `SQL Request Mode`, `SQL Request Status`, `User Name`,
`AL Object Type`, `AL Object Name`, `AL Method Scope`.

**Цепочки «кто кого» она не даёт принципиально.** SQL под ней (константа
`SelectDatabaseLocksCommand`) выбирает только `request_owner_id`, имя объекта, тип
ресурса, режим и статус запроса. Ни `request_session_id`, ни `blocking_session_id`, ни
`resource_description` там нет вовсе, а `request_mode LIKE 'I%'` и `Sch-%` отброшены.

**Имя пользователя и объект AL платформа подставляет сама**, по своей карте
«транзакция → сессия» (`DatabaseLocksDataProvider.GetTransactionSessionMapForTenant`).

**На живой блокировке двух сессий NAV таблица вернула НОЛЬ строк** — и стороннему
наблюдателю, и самому держателю, читавшему её изнутри своей же открытой транзакции.
Чтение проходит успешно и быстро (85 мс), набор пуст.

Причина доведена до строки кода. `AddDatabaseLockToRecordList` выбрасывает строку, если
`transaction_id` не найден в карте. Карту наполняет `CurrentTransactionId` каждой сессии,
а он заполняется в `NavSqlConnection.BeginTransaction` только при взведённом
`ConnectionPool.TransactionHistory`. `EnableTransactionHistory()` зовётся ровно один раз —
в `NavEnvironment.SetupDeadlockAnalyzer`, на одноразовом обработчике `DatabaseFirstAccess`,
и только при `EnableDeadlockMonitoring=true`. На стенде — `false`.

Тот же запрос платформы, выполненный руками и **от имени учётки службы**
(`EXECUTE AS LOGIN`), честно вернул обе ожидаемые строки. Дело не в правах и не в
лицензии — строки выбрасывает сам провайдер.

### Чем платят за включение

| Что требуется | Подробность |
|---|---|
| `EnableDeadlockMonitoring=true` | правка `CustomSettings.config` |
| Перезапуск экземпляра | взвод висит на `DatabaseFirstAccess`, права снимаются один раз |
| **Оба** права SQL | `VIEW SERVER STATE` И `ALTER ANY EVENT SESSION`; проверяются запросом `HAS_PERMS_BY_NAME` один раз при первом обращении к БД |
| Постоянная серверная сессия XE | `<База>_deadlock_monitor`, `STARTUP_STATE=ON`, **переживает снятие инструмента** — убирает её только обратное выключение ключа |
| Надбавка на каждой транзакции | `SELECT TOP 1 transaction_id FROM sys.dm_tran_session_transactions WHERE session_id = @@spid` на КАЖДОМ старте транзакции в КАЖДОЙ сессии (0,062 мс против 0,083 мс у `SELECT 1` на 500 прогонах — но на выносном сервере это сетевой круг) |

**Отказ невидим.** Не выдали право — платформа пишет одну строку трассировки уровня
Warning, и таблица ведёт себя в точности как при отсутствии блокировок. Экран будет пуст
и на здоровой системе, и на сломанной.

### Три скрытых отбора

1. Компания владельца блокировки обязана совпасть с компанией **читающей** сессии
   (исключение — таблицы с `DataPerCompany=No`). Один наблюдатель не увидит чужой компании.
2. Intent- и схемные блокировки отброшены — а на живом сервере это большинство строк.
3. Всё, что держит не сессия NAV этого тенанта с текущим соединением, не появится
   никогда: чужой экземпляр службы, внешнее подключение, собственная обёртка ADO.NET.

### И колонки AL отвечают не на тот вопрос

`AL Object Type / Id / Method Scope` берутся из **живого стека виновника в момент
чтения** (`CurrentMethodScope.StackTrace?.LastOrDefault()`) — самый глубокий кадр СЕЙЧАС,
а не тот, что взял блокировку. Длинная проводка держит блокировку и уходит через десятки
кодюнитов: два соседних опроса одного эпизода назовут разные объекты.

### Цена чтения

2,8 мс при 12 блокировках; **157,5 мс и 30 001 строка** при 30 тысячах. Провайдер
`EagerVirtual`: любое чтение, даже `FINDFIRST` с отбором, материализует ВСЕ блокировки
экземпляра и обходит ВСЕ живые сессии. То есть дороже всего он именно в шторм.

## 3. Сторона SQL: работает уже сегодня

`VIEW SERVER STATE` учётной записи службы **уже выдан явным GRANT**, sysadmin у неё при
этом нет (проверено `EXECUTE AS`).

**Цепочка «кто кого» снимается одним запросом за 0,64 мс** (`sys.dm_os_waiting_tasks` +
`sys.dm_exec_sessions`): жертва, виновник, тип и режим ожидания, миллисекунды ожидания,
ресурс с `hobt_id`, состояние виновника и номера транзакций обеих сторон. Живой пример со
стенда: держатель — сеанс NAV 270, spid 75, транзакция 988137, `KEY U GRANT`; жертва —
сеанс 272, spid 98, транзакция 988924, `KEY U WAIT`, `LCK_M_U`.

**Виновник СПИТ.** `status=sleeping`, строки в `dm_exec_requests` у него нет вовсе — его
последний оператор достаётся только через `dm_exec_connections.most_recent_sql_handle`.
У жертвы, наоборот, строка есть, и её точный ждущий оператор берётся по
`statement_start_offset/end_offset`.

**`resource_description` уже несёт `hobt_id`** — заходить в дорогую `dm_tran_locks` ради
ресурса не нужно.

**Мост «транзакция → сессия» строить по ДВУМ DMV.** Сторона внутри транзакции резолвится
через `dm_tran_session_transactions`; автокоммитный оператор — нет: его `transaction_id`
есть в `dm_exec_requests`, а в `dm_tran_session_transactions` его нет вовсе. У NAV пишущая
сторона всегда в транзакции, а вот жертва-читатель — не всегда.

**Предел ожидания блокировки у NAV — 10 000 мс.** Замерено дважды: жертва умирала на
10 099 и 10 120 мс со штатным текстом «запись заблокирована другим пользователем». После
отказа она исчезает из `dm_os_waiting_tasks` мгновенно.

**Подарок: номер объекта NAV лежит прямо в тексте запроса.** Платформа даёт таблице
псевдоним, равный номеру объекта: `SELECT TOP (1) "110201"."timestamp","110201"."Entry No_"`.

## 4. Цена наблюдения — главная поправка

Первоначальное «цена плоская по числу блокировок» **измерено не по той оси**.
`sys.dm_os_waiting_tasks` дорожает по числу **ждущих задач**, а разведка меняла число
блокировок, держа одну-две ждущих.

Из C/AL, тем самым транспортом (DotNet `SqlClient`), 500 прогонов на прогретом плане:

| Ждущих задач | Пульс | Полная цепочка |
|---|---|---|
| 0 | 0,12 мс | 0,29 мс |
| 60 | 2,08 мс | 5,95 мс |
| 200 | **11,95 мс** | 21,60 мс |

Со стороны SQL: 36 ждущих → 0,106 мс; 236 ждущих → **7,87 мс** (рост в 74 раза), при том
что блокировок было всего 609. **Отбор не спасает**: тот же запрос с заведомо пустым
условием — 7,83 мс, голый `COUNT(*)` — 7,88 мс. Дешёвого сторожа на этом DMV нет.

Для контроля: чтение 300 строк из `sys.objects` стоило 5,3 мс и от шторма не зависело —
дорожает не маршалинг строк в C/AL, а само перечисление ждущих задач.

### Способы наблюдения, от дешёвого к дорогому

| Способ | Цена | Что даёт | Права |
|---|---|---|---|
| `sys.dm_db_index_operational_stats(DB_ID(),…)` | **0,46–0,6 мс** на всю базу, 220 строк | накопительно по таблице и ключу: сколько раз и сколько мс ждали, эскалации. **Видит SIFT** | **никаких сверх имеющихся** — читается при `VIEW SERVER STATE = 0` |
| `sys.dm_os_wait_stats` по `LCK_*` | 0,44 мс | итог по экземпляру, масштаб беды | даром |
| `system_health` ring buffer | 37 мс за чтение | `xml_deadlock_report` целиком, без настройки. `blocked_process_report` там **нет** | `VIEW SERVER STATE` |
| `dm_os_waiting_tasks` + `dm_exec_sessions` | 0,1 мс праздно, **12 мс в шторм** | «кто кого», ресурс, ждущий оператор | `VIEW SERVER STATE` |
| `sys.dm_tran_locks` | 3,1 мс праздно, 45,6 мс при 60 тыс. | в цикл **не ставить**, отбор не помогает | `VIEW SERVER STATE` |
| `blocked_process_report` | дёшев по устройству | см. ниже | правка настройки СЕРВЕРА (sysadmin) + своя сессия XE |
| `lock_acquired` / `lock_released` | событие на каждую блокировку | **не брать** | — |

### `blocked_process_report`: разведка ошиблась дважды

Дешевизна **подтвердилась и объяснима**: отчёт поднимает уже работающая фоновая задача
`LOCK MONITOR`, расход пропорционален числу ждущих дольше порога, а не числу блокировок.
Замерено: на блокировку длиной 17 с при пороге 5 с пришло ровно 3 отчёта.

Но **готовых `object_id`/`index_id` он не даёт**. Они верны только для `OBJECT`-блокировки;
на обычной построчной `KEY`-блокировке — ради которой всё и затевается — там мусор:
`rep_object_id=16992` при настоящем `1461580245`. Настоящий ресурс лежит только в XML.
И в этом же XML едет **полный текст операторов обеих сторон со значениями** — для службы
безопасности это выгрузка данных, а не структура.

## 5. Разбор имени: два правила, а не одно

**Имя таблицы NAV** из имени SQL: `[Компания]$[Имя таблицы]`, где `. / \ "` заменены
подчёркиванием, а у таблиц с `DataPerCompany=No` префикса компании нет вовсе. Обратная
карта покрывает 2526 из 2545 пользовательских таблиц; непокрытые 19 — платформенные
`$ndo$*`. Ни одна таблица NAV не теряется.

**Номер ключа NAV** — суффикс имени индекса после последнего `$`. Тонкости: у кластерного
индекса имя полное (`…$0`), у вторичных просто `$1`, `$5`, `$13`; номера **не сплошные**
(у выключенных ключей индекса в SQL нет); `index_id` и номер ключа NAV — разные вещи.

**Карту строить один раз (28 мс) и держать в памяти.** Поштучное разрешение стоит 19,1 мс
за блокировку — в цикле недопустимо.

### SIFT ломает оба правила, и это самый частый случай

Классическая блокировка NAV садится не на таблицу, а на её **SIFT-представление**.
Проверено опытом на индексированном представлении-агрегате: два сеанса, вставляющие
**РАЗНЫЕ** строки, столкнулись на общей корзине агрегата —
`row_lock_wait_in_ms = 2047` у представления и **ноль** у базовой таблицы.

В базе стенда **308 представлений `VSIFT`** над 154–187 таблицами, имена вида
`<Компания>$<Таблица>$VSIFT$<n>`, и индекс у всех один и тот же — `VSIFTIDX`. Отсюда:

- карта, построенная по `sys.tables`, их не покрывает: `VIEW` — разрешено 4, **не
  разрешено 311**;
- правило «номер ключа из суффикса имени индекса» на них даёт `VSIFTIDX` — цифр нет.

Лечение: в карту класть и `sys.views`; имя разбирать по **последнему** вхождению
`$VSIFT$` — левая часть даёт таблицу, правая номер ключа. Ожидания представления
подкладывать под базовую таблицу, но **отдельной колонкой** «в т.ч. на SIFT-агрегате,
ключ N»: это и есть готовый ответ на «из-за чего» — не конкуренция за строку, а
поддержание агрегата, и лечится `SumIndexFields`, а не индексом.

Строку, чей hobt не разрешился, **никогда не выбрасывать**: показывать сырым именем с
пометкой «не опознано» и считать счётчиком. Молчаливый пропуск — это и есть ложь.

### Две молчаливые ловушки разбора

`OBJECT_NAME` без второго аргумента разрешает имя в базе **вызывающего** и возвращает
правдоподобное ЧУЖОЕ имя — фильтр по `resource_database_id` обязателен. И `OBJECT_NAME`
от `hobt_id` роняет запрос переполнением int: ветвление по `resource_type` обязательно.

## 6. Фоновая работа: только `TASKSCHEDULER`

Единственный механизм, дающий работу без клиента, которая переживает перезапуск службы
(задача лежит строкой в базе, есть владелец-экземпляр и heartbeat, платформа умеет
восстанавливать задачи умершего экземпляра) и имеет обработчик падения — Failure Codeunit.

- **Job Queue** — прикладная обёртка над ним же; на целевом контуре доработана заказчиком,
  вешаться туда — зависеть от чужих правок и делить чужой лимит.
- **`STARTSESSION`** — только разовый запуск и запасной путь, когда `CANCREATETASK` вернул
  `FALSE`: ни отложенного старта, ни обработчика ошибок, ни переживания рестарта.
- **NAS и своя служба Windows** — отпадают: лицензия и правка конфига у первого, прямое
  нарушение обещания «ни служб, ни планировщика» у второй.

Проверено на стенде: задача поднялась (`ClientType=Background`), `SLEEP(2000)` точен
(интервалы 2,006–2,037 с), `DotNet SqlClient` из фоновой сессии работает, задача заняла
ровно один слот планировщика на всё время жизни.

**Два ограничения записать сразу.** Постановка задачи требует `COMMIT` (внутри незакрытой
транзакции она не создастся). `MESSAGE` из фоновой сессии уходит в журнал событий NAV, а
не на экран — фоновому коду нужен свой способ отчитаться.

**И один потолок.** `TooManyRunningTasks()` при 10 незавершённых задачах заставляет
планировщик выйти НЕ ЗАПУСТИВ НИЧЕГО. Долгоживущая задача постоянно держит 1 слот из 10,
делимых с заданиями заказчика: цикл должен быть коротким и перевзводить себя, а не жить
вечно одной задачей.

## 7. ETW: запасная дорога к именам, не требующая прав SQL

Каталог событий провайдера NAV, снятый с этого стенда:

```
id=402 kind=FuncFail  fields=navTenantId,sessionId,userName,objectType,objectId,
                             functionName,failureMessage,serverInstanceName,…
id=11/12 task=6       fields=navTenantId,sessionId,userName,serverInstanceName
id=1..10 kind=Sql*    fields=navTenantId,sessionId,userName,sqlStatement,serverInstanceName
id=403 kind=Statement fields=navTenantId,sessionId,objectType,objectId,functionName,
                             lineNumber,statement,…
```

**Учётка NAV и номер сеанса лежат в каждом событии**, у отказа — ещё объект, функция и
текст ошибки. Прав SQL не нужно вовсе: приёмник сидит внутри процесса службы.

**Идентификатора соединения SQL нет ни в одном событии** — сшить ETW с блокировкой на
стороне SQL нечем. Это самостоятельная дорога, а не мост.

Что из этого следует (вывод, не замер): жертву можно назвать поимённо без единого права
SQL, а виновника — только списком подозреваемых «кто держал открытую транзакцию с записью
в эту таблицу в момент отказа».

**Не проверено вживую, и это две дырки:**

1. приходит ли `FuncFail` на отказ по блокировке;
2. идут ли SQL- и транзакционные события **без** `EnableFullALFunctionTracing` — если для
   них нужен тот же флаг, что для построчного профайлера, цена ровно та, от которой мы
   бежим (событие на каждый оператор C/AL, весь сервер медленнее, плюс перезапуск).

## 8. Номера объектов и прецедент безопасности

`110210–110259` на стенде пусты полностью; `110200–110209` заняты (17 объектов профайлера
и приватные вспомогательные, вперемешку по типам). **Разрешённый лицензией ЗАКАЗЧИКА
диапазон неизвестен**: лицензия стенда внутренняя сборочная и перечня диапазонов не
содержит вовсе. И проверять надо столкновение **по имени тоже** — на стенде уже есть
нештатные объекты с именем «Database Lock».

LineProfiler прошёл согласование не потому, что просил мало, а потому, что каждое
требование объяснил, снабдил командой проверки и колонкой «а если не дадите», и отдал
службе безопасности рычаг: два права SQL объявлены необязательными, съём реальных данных
выключен по умолчанию, имена чужих пользователей не читаются вовсе.

LockWatch делает **два разворота** против этого прецедента: он ПОКАЗЫВАЕТ учётки других
людей и копит журнал ФОНОМ, а не внутри окна «Старт—Стоп». Значит взамен обязан отдать
больше: одно право уровня сервера вместо sysadmin, никакой правки `CustomSettings.config`
и перезапуска, по возможности без сборки .NET в `Add-ins` вовсе, значения данных —
отдельной выключенной галкой, и объявленный срок хранения журнала с автоматической
чисткой, которого у профайлера нет.

## 9. Обратный поиск по хэшу ключа: проверено на схеме целевой установки

Стенд второй, и он важнее первого: полный набор объектов целевой установки на своей
NAV 2018 — **3 055 таблиц, 5 984 индекса, 248 представлений `VSIFT`**. Имя базы — в
`LW_DATABASE`. Замеры 07.09.2026, служба NAV при этом остановлена: всё ниже снимается
одним SQL и работающего экземпляра не требует.

**Хэш ключа обратим.** `resource_description` у `KEY`-блокировки — это хэш значений ключа,
и строка по нему находится запросом `WHERE %%lockres%% = '(…)'`. Проверено насквозь на
настоящей блокировке: сессия взяла `UPDLOCK` на строку штатной `Table 17 «G/L Entry»`,
наблюдатель со стороны увидел `KEY U`, хэш `(92410d4f079d)` и транзакцию 12337914,
разрешил хэш по индексу из `hobt_id` и получил **ровно ту строку**. Цена — 2,3 мс на
4 149 строк, то есть скан индекса.

Это и есть мост из раздела 7.2 [JOURNAL.md](JOURNAL.md): «транзакция виновника → её
блокировки → строка» — не корреляция, а факт, и он работает.

**Хэш считается по КОНКРЕТНОМУ индексу, и ошибка индекса не видна.** Одна и та же строка
даёт `(61a06abd401c)` на кластерном индексе и `(25d1acec8a76)` на вторичном. Поиск по хэшу
вторичного без `INDEX(...)` возвращает **пустой набор и никакой ошибки**. Значит
пропущенное ветвление по индексу выглядит как «строка не найдена» — ровно тот молчаливый
отказ, который дороже всего искать потом.

**Ветвление окупается почти всегда.** У NAV вторичный ключ уникален и несёт поля
кластерного ключа хвостом: из **2 930 вторичных индексов базы 2 903 содержат весь
кластерный ключ**, и только 27 — нет. Блокировка почти на любом индексе таблицы-контекста
разрешается в строку, у которой номер документа на месте; способ не ограничен кластерным.

**`resource_description` приходит добитым пробелами** до ширины столбца DMV. Сравнение
`%%lockres%% = @res` это переживает — SQL игнорирует хвостовые пробелы, — а вот склейка
хэша в текст запроса не переживает. Обрезать при чтении.

**Поправка к цене накопительного слоя.** На этой базе
`sys.dm_db_index_operational_stats` вернула **136 строк за 1,3 мс** против 220 строк за
0,6 мс на первом стенде — при том что таблиц здесь в двенадцать раз больше. DMV отдаёт
строки только по объектам, у которых была активность с последнего перезапуска, поэтому её
размер зависит от НАГРУЗКИ, а не от схемы. Планировать объём журнала по числу таблиц нельзя.

## 10. Что видно по исходникам объектов целевой установки

Выгрузка объектов целевой установки — 13 835 объектов, вне репозитория, путь в
`local/stand.md`. Прочитано 07.09.2026.

**Диапазон `110230` и выше свободен на живом наборе.** Занято `110200–110207` —
семнадцать объектов профайлера; выше и до `110400` пусто. И столкновений **по имени** со
словом «Lock» среди 13 835 объектов нет ни одного: единственный носитель имени
«Database Locks» — штатная `Page 9511`. Предостережение раздела 8 относилось к другому
стенду и на целевую установку не переносится.

**Врезка в чужой код НЕ НУЖНА: есть подписка на события таблицы.** Платформа 11 поднимает
глобальные события таблиц, и целевая установка ими уже вовсю пользуется — 108 подписок на
`OnAfterInsertEvent`, 76 на `OnAfterModifyEvent`, 73 на `OnAfterDeleteEvent`. Синтаксис в
тексте объекта:

```
[EventSubscriber(Table,37,OnAfterModifyEvent)]
LOCAL PROCEDURE OnAfterModify@1(VAR Rec@1000 : Record 37;VAR xRec@1001 : Record 37;RunTrigger@1002 : Boolean);
```

Подписчик исполняется **внутри транзакции пишущего** — ровно то, что нужно записи
контекста ([JOURNAL.md](JOURNAL.md), раздел 7.2): отметка ложится в ту же транзакцию, и
её собственная блокировка становится мостом. Значит путь к имени и номеру, который
казался самым дорогим, **не требует ни одной правки в объектах заказчика**.

**Но номер таблицы в подписке — константа времени компиляции**, и типизированный параметр
`Record <номер>` тоже. Настройкой это не обходится: подписчик на таблицу контекста —
отдельный маленький объект-переходник, свой для каждой установки. В репозитории он живёт
**шаблоном** со штатной таблицей в примере, боевой номер подставляется на месте. Отсюда
правило: список таблиц контекста в настройке отвечает за РАЗБОР, а переходник — за СЪЁМ,
и сторож обязан ругаться, когда в настройке есть таблица, для которой переходника нет.

**SIFT целится не туда, куда казалось.** Из 158 таблиц с `SumIndexFields` клиентских
всего 7 — остальное штатные регистры. SIFT-блокировки будут приходить на штатных
таблицах, а таблицы документов заказчика от них свободны; у самой таблицы контекста
представлений `$VSIFT$` нет вовсе, и ключ у неё одиночный. Для номера документа это
означает разбор без составного ключа.

**Поправка к разделу 6.** Диспетчер очереди заданий (`Codeunit 448`) и стартовый кодюнит
`449` на целевой установке **не тронуты**, они штатные; доработаны только `Table 472` и её
карточка — заказчик добавил свои поля. Значит довод «очередь доработана заказчиком» верен
наполовину: чужих правок сам механизм не несёт. Против очереди остаётся другое — она
общая, с общим лимитом и общим администрированием, и запись задания в ней видна и
редактируема тем, кого мы наблюдаем.

## 11. `resource_description` — их два, и они разные

Замер 07.09.2026 на настоящем ожидании: держатель взял `XLOCK` на строку, жертва встала за
`UPDLOCK` на ту же строку, съём шёл с третьего соединения.

**В очереди ожиданий** (`sys.dm_os_waiting_tasks`) описание ресурса выглядит так:

```
keylock hobtid=72057594261667840 dbid=7 id=lock1870ff96880 mode=X associatedObjectId=72057594261667840
```

Есть род ресурса (`keylock`), `hobtid`, номер базы, адрес блокировки в памяти и `mode`
**держимой** блокировки. **Хэша ключа здесь нет.** Значит из дешёвого опроса очереди
строку назвать нельзя в принципе: он отвечает «какая таблица и какой ключ», а не «какая
запись».

**В `sys.dm_tran_locks`** та же блокировка описана иначе: `resource_description` несёт
только хэш `(92410d4f079d)`, а `hobt_id` лежит отдельным столбцом. Зато одной выборкой
видны обе стороны — виновник `KEY X GRANT`, жертва `KEY U WAIT`, хэш один и тот же.

Отсюда поправка к устройству: **и 7.1, и 7.2 [JOURNAL.md](JOURNAL.md) требуют одного
чтения `dm_tran_locks` на эпизод** — именно оно приносит хэш. Это не два обращения, а
одно общее, и делается оно после закрытия эпизода, вне цикла опроса. Дешёвый опрос
очереди при этом остаётся дешёвым и отвечает на свой вопрос: кто кого, на какой таблице и
ключе, сколько ждут.

Попутно: `dbid` в тексте очереди есть, поэтому отбор по своей базе снимается разбором, а
не отдельным столбцом. И `mode` в тексте — это режим держимой блокировки, тогда как
`wait_type` (`LCK_M_U`) говорит, чего хочет жертва: подписывать их одним словом нельзя.

**Предел 10 000 мс — это предел NAV, а не SQL.** В этом же опыте жертва-сессия SQL
прождала 10 527 мс и продолжала ждать: `LockTimeout` у неё нет. Значит правило исхода
эпизода ([JOURNAL.md](JOURNAL.md), раздел 3) применимо только к сессиям NAV; ожидание
внешнего подключения или задания обслуживания может быть сколь угодно долгим, и метить
его «отказ по пределу» нельзя. Сессию надо сперва опознать как NAV — по `program_name`,
`host_name` и `host_process_id`, — и только потом судить об исходе.

## 12. Дешёвого триггера нет: накопительные счётчики молчат, пока эпизод идёт

Замер 07.09.2026 — три чтения вокруг одного настоящего ожидания, держатель `XLOCK`,
жертва `UPDLOCK`, съём с третьего соединения.

| Момент | `row_lock_wait_count` | `row_lock_wait_in_ms` | `Processes blocked` | Очередь |
|---|---|---|---|---|
| до опыта | 1 | 28 469 | 0 | 0 |
| **на пятой секунде ожидания** | **1** | **28 469** | 1 | 1 |
| после окончания | 2 | 49 266 | 0 | 0 |

`sys.dm_db_index_operational_stats` **не шевелится, пока ожидание идёт**: счётчик прирастает
одним куском в тот момент, когда ожидание ЗАКОНЧИЛОСЬ. Значит замысел «дешёвый триггер по
накопительным счётчикам, а очередь опрашивать только по нему» неработоспособен в самом
основании: триггер сработает тогда, когда в очереди уже никого нет, и опрос по нему увидит
пустоту. Так терялся бы КАЖДЫЙ эпизод — и, что хуже, тихо: журнал был бы пуст и на
здоровой системе, и на стоящей.

**Счётчик «Processes blocked» живой, но запаздывает.** `sys.dm_os_performance_counters`
отдаёт мгновенное число заблокированных процессов и стоит **0,18 мс** за чтение. Но
занятость он показал **на 1 655 мс позже**, чем ожидание появилось в очереди: счётчик
обновляет фоновая задача сервера, а не читатель. Вдобавок он требует того же
`VIEW SERVER STATE`, что и очередь, — на уровне 0 недоступен, значит и прав им не сберечь.

**И экономить, как выяснилось, нечего.** Цена чтения, 200 повторов на прогретом плане:
`dm_db_index_operational_stats` по всей базе — **0,33 мс**, счётчик — **0,18 мс**, пустая
очередь — доли миллисекунды. Дорогое чтение очереди (12 мс при двухстах ждущих) бывает
только в шторм, а 12 мс раз в несколько секунд — это доли процента одного ядра. Бояться
надо не DMV, а NAV-половины прохода: поиска эпизода в журнале, записи и `COMMIT` на сотни
строк. Она измерена в разделе 13 и оказалась в тридцать раз дороже съёма.

**Вывод: триггер убрать, очередь опрашивать прямо.** А накопительный слой возвращается к
своей настоящей роли — он не сторож, он ЧЕСТНЫЙ ИТОГ: считает в том числе ожидания, которые
опрос проспал, потому что они короче периода. Отсюда даровая самопроверка охвата, которой
в замысле не было: «за час счётчики насчитали X мс ожиданий, журнал видел Y» — доля
покрытия пишется прямо на экран, вместо молчаливого обещания, что видно всё.

## 13. Цена NAV-половины прохода: 0,8 мс на строку, 408 мс на потолок

Единственное число, которое всё это время жило на обещании. Меряется мерным прогоном
(`Codeunit 110233`) прямо на стенде: журналу подаются разобранные строки очереди, поэтому
ожиданий устраивать не нужно вовсе, и мерить можно сколько угодно.

Четыре прогона, **500 строк за проход** — ровно объявленный потолок:

| Проход | Время | На строку |
|--------|-------|-----------|
| открытие 500 эпизодов | 338–408 мс | 0,7–0,8 мс |
| обновление тех же 500 | 242–299 мс | 0,5–0,6 мс |
| закрытие 500 | 94–126 мс | 0,2–0,3 мс |
| уборка 490 строк | 2–15 мс | 0,03 мс |

Каждый проход — **вместе с `COMMIT`**: без него замер вдвое красивее и вдвое бесполезнее,
потому что запись в журнал транзакций и есть то, чем проход платит.

**Вывод: укладывается, но запас не бесконечен.** Худший проход — 408 мс при потолке 1000 и
периоде 3000, то есть около седьмой части времени между проходами. Съём с DMV на том же
шторме стоит 12 мс — в тридцать раз дешевле. **Дорога именно NAV-половина, и бояться надо
было её**, как и написано в разделе 12.

Разброс между прогонами доходит до пятой части: стенд делит машину с SQL. Поэтому обещать
можно «укладывается в потолок с запасом вдвое», но не конкретные миллисекунды.

**Что из этого следует для устройства:**

- Эпизод **обязан** быть строкой, которая обновляется. Обновление вдвое дешевле открытия,
  а снимками журнал платил бы цену открытия каждые три секунды.
- Номер записи снимается с конца **один раз за жизнь задачи**, а не на строку: иначе к
  цене прохода добавилось бы полтысячи чтений последней страницы.
- `COMMIT` — **один на проход**. На строку он превратил бы 0,8 мс в единицы миллисекунд.
- Потолок в 500 строк не декоративный: на 2 000 ждущих проход перевалил бы за период, и
  наблюдатель начал бы догонять сам себя. Отсюда отметка «усечён» вместо тихого отставания.

Проверено поломкой, оба раза краснеет ровно то, что должно: снятый отбор по сроку в чистке
даёт «убрано 500 из 10 состаренных» (месяц наблюдений вынесен за один проход), а опознание
эпизода вместе с длительностью — «обновлено 0, открыто 500, строк в журнале 1000».

## 14. Съём проверен на живой блокировке, и два места соврали бы молча

Проход целиком — от очереди SQL до строки в журнале — проверяется на **настоящей**
блокировке: два соединения `sqlcmd` дерутся за одну строку, инструмент снимает очередь,
и журнал сверяется с тем, что на самом деле происходит на сервере
(`scripts/Test-Pass.ps1`, десять проверок).

**Как инструмент разговаривает с SQL.** Своё соединение через штатную `System.Data`
из фреймворка — **сборки в `Add-ins` нет вовсе**, и это снимает четыре строки из семи в
таблице прав. Имя базы спрашивается у платформы (`Record 2000000110 "Active Session"`),
имя сервера — у человека в настройке: в той же строке платформы записан сервер **NAV**, а
не сервер базы, и подставить одно вместо другого значит наблюдать не за той базой, ничего
об этом не узнав.

**Ловушка первая: в DMV половина целых — `smallint`.** `session_id`, `blocking_session_id`
и `DB_ID()` — не `int`, и `SqlDataReader.GetInt32` на них падает с
`Specified cast is not valid`. Отказ приходит на **первой же строке очереди**, то есть
ровно тогда, когда блокировка наконец случилась; на тихом сервере всё выглядит исправным.
Лечение — `CONVERT(int, …)` на каждое целое, а не на подозрительные.

Поймал это **сторож**, а не человек: проход не упал, а записал в настройку
«Очередь прочитать не удалось: …GetInt32 failed…». Ради этого он и заведён — молча
проглоченный отказ дал бы пустой журнал, который читается как «блокировок не было».

**Ловушка вторая: `Start-Process` не берёт запрос параметром.** Элементы `-ArgumentList`
склеиваются пробелом **без кавычек**, поэтому `-Q "SET LOCK_TIMEOUT -1; BEGIN TRAN; …"`
рассыпается на аргументы, `sqlcmd` выходит с ошибкой, и опыт выглядит как «блокировка не
случилась». Запрос уезжает **файлом** (`-i`).

**Что подтвердилось на живом ожидании:**

| Проверка | Ответ инструмента |
|---|---|
| жертва и непосредственный виновник | те самые номера сеансов |
| описание ресурса | `KEYLOCK`, `hobt 72057594815315968`, ждёт `LCK_M_U` |
| имя из SQL в таблицу и ключ NAV | таблица и **ключ 0** (кластерный) |
| цепочка | голова, глубина 1, жертв за головой 1 |
| чужая сессия | названа чужой |
| после ухода из очереди | эпизод закрыт, конец позже начала |
| исход у чужой сессии | **не определён** |

Последняя строка — самая важная. Предел 10 000 мс принадлежит NAV, а не серверу, и
приписать его соединению `sqlcmd` значило бы выдумать факт: правдоподобный и ложный.

## 15. Сторож идёт сам, и проверено это тем, что никто ничего не нажимал

Собравшаяся фоновая задача, которая ни разу не проснулась, — текст, а не наблюдение.
Поэтому в `scripts/Test-Watch.ps1` вручную вызываются ровно две вещи: «завести» и
«остановить». Эпизод обязан появиться в журнале **сам** и закрыться тоже сам.

Семь проверок, и все зелёные на стенде 07.09.2026: завод ставит ровно одну задачу; проход
случается без нажатия; цепочка перевзводится и **не раздваивается**; сторож ловит
настоящую блокировку сам; эпизод закрывается сам; остановка снимает и выключатель, и
задачу; после остановки проходов больше нет.

**Своя цепочка `TASKSCHEDULER`, а не Job Queue** — как и решено в разведке. Задача
перевзводит себя в конце каждого прохода, и держится это на трёх решениях:

- проход зовётся через `CODEUNIT.RUN`: ошибка внутри откатит его транзакцию, но не уронит
  задачу. Без этого цепочка оборвалась бы на первой неожиданности, ночью и молча;
- выключенный сторож обрывает цепочку сам и **пишет об этом**;
- завод идемпотентен: сначала снимаются свои задачи, потом ставится одна.

**Обратная связь — только на разрежение.** Наблюдатель не берёт себе больше **одной
десятой** времени: следующий проход откладывается на `10 × длительность последнего`, если
это больше периода. Учащение при занятости было бы разгоном самого себя — в шторм проход
дорожает, и наблюдатель добил бы сервер, который пришёл лечить.

### Ошибка, которую нашёл прогон, и две ловушки, которые он же и поймал

**Выключатель перечитывался один раз, а надо два.** `Reschedule` перевзводил цепочку, не
перечитав «включён»: нажатое во время прохода «стоп» отменялось бы перевзводом, и сторож
воскресал бы сам — ровно один раз, и объяснить это было бы нечем. Исправлено. Честно
говоря сразу: **прогоном это не ловится** — окно длиной в проход открыто пять миллисекунд
из трёх секунд, и попасть в него нарочно нельзя. Проверка здесь одна, чтение кода.

**`;` внутри `ToolTipML` начинает новый язык.** Импорт падает с тем же
`… is not an option. The existing options are:`, что и `=` внутри `TextConst`, и причину
так же не называет. Проверять надо все ML-свойства разом — сканером, а не по одному отказу
за прогон.

**Строку настройки нельзя обнулять запросом мимо NAV.** Однострочная таблица лежит в кэше
службы: `UPDATE` до сессии не доходит, а первое же обращение кода к настройке запишет
кэшированную строку обратно — вместе с полями, которые запрос обнулил. Со стороны это
выглядит как «поле воскресло само», и прогон краснеет не по делу. В прогонах прежнее
значение **запоминается**, и проверка ждёт его изменения.

**`sqlcmd` по умолчанию рвёт строку на 80 знаках.** Длинное значение приходит двумя
строками, и проверка, читающая первую, судит по обрезку. Лечится `-w 500`, и это не
мелочь: именно так сообщение сторожа читалось наполовину.

## 16. Проход целиком под нагрузкой: 90 мс на сотне ждущих, и разовые 414 мс на старте

Съём и запись меряны порознь, и складывать два замера в уме — это не замер, а надежда.
`scripts/Test-Load.ps1` устраивает **сотню настоящих ждущих** (один держатель, сто
соединений за ним в очереди, все в одном процессе) и меряет то, что делает фоновая задача:
проход целиком, длительность берётся из настройки, куда её пишет сам NAV.

| Проход, 100 ждущих | Время | На строку |
|---|---|---|
| первый после перезапуска службы | **494 мс** | 4 940 мкс |
| обновление, установившийся режим | **80–106 мс** | 800–1 060 мкс |
| закрытие сотни эпизодов | 27 мс | 270 мкс |

**Первый проход после перезапуска дороже установившегося на 414 мс, и это разовая цена:**
платформа поднимает сборку `System.Data`, соединение открывается впервые, сервер
компилирует планы. Выдать её за цену наблюдения значило бы напугать заказчика тем, чего
не будет. Проверка в прогоне на это и смотрит — что установившийся проход **заметно**
дешевле первого.

Заодно это первый живой случай, когда сработало правило разрежения: после холодного
старта проход стоил 494 мс, и следующий отложился на 4 940 мс вместо 3 000. На втором
проходе всё вернулось к периоду. Разгона себя не случилось — как и задумано.

**Сходится ли с замерами по частям.** NAV-половина на 500 строк стоит 568 мкс на строку
(раздел 13), то есть на сотне — около 57 мс. Проход целиком на сотне — около 93 мс.
Значит съём с SQL вместе с постоянными расходами прохода стоит около **36 мс**, что
согласуется с 12 мс на чтение очереди при двухстах ждущих (раздел 1) плюс запрос имён
плюс два открытия соединения. Арифметика сошлась, и теперь она подтверждена, а не
предположена.

**Что проверено заодно:** проход видит всю очередь и не усекается на сотне; второй проход
не плодит строк; **сто жертв за одной головой сосчитаны как одна беда** (голов 1, глубина 1);
ушедшая очередь закрывает все сто эпизодов.

Три ловушки прогона, все про `Start-Process` и генерацию скриптов: аргумент со скобками и
пробелами рассыпается (имя таблицы уехало параметром — процесс тихо умер); `$` внутри
двойных кавычек СГЕНЕРИРОВАННОГО скрипта раскрывается как переменная, и
`[Компания$Таблица]` превратилось в `[Компания Таблица]`; толпу надо делать одним
процессом с сотней соединений, а не сотней процессов — память рабочей станции уже однажды
уронила SQL Server.

## 17. Номер документа и имя виновника — без единого нового права

Ради этого всё и затевалось, и до сих пор колонка «Документ» была пуста. Теперь мост
построен и **проверен на живой блокировке** (`scripts/Test-Pass.ps1`, двенадцать проверок):

```
документ [HELD], откуда 2 (по отметке контекста), причина []
учётная запись [STAND], откуда 1 (по отметке)
```

**Это не корреляция по времени, а факт.** Подписчик кладёт отметку в ТОЙ ЖЕ транзакции,
что и запись виновника, поэтому транзакция виновника держит на отметке монопольную
блокировку. Дальше цепочка сплошь из фактов: номер транзакции (он и так в журнале) →
её блокировка на нашей таблице → хэш ключа → обратный поиск `%%lockres%%` → строка →
документ и учётная запись.

**Имя человека получено без `EnableDeadlockMonitoring`** — без правки конфига, без
перезапуска экземпляра, без обоих прав SQL и без постоянной серверной сессии Extended
Events. Оговорка честная и важная: это имя **виновника**, взятое из его же транзакции, а
не имя, которое называет платформа. Обещать «имена людей» по-прежнему нельзя — обещать
можно «учётную запись того, кто держит блокировку, если он писал в таблицу контекста».

### Три решения о цене, каждое проверяемое

- **`dm_tran_locks` читается один раз на ПРОХОД, а не на эпизод.** Сто жертв за одним
  виновником дают один номер транзакции, и скан по шестидесяти тысячам блокировок
  платится единожды. На тихом сервере он не платится **вовсе**: разбирать нечего — запрос
  не идёт. Это и есть исполнение правила «в цикле не трогать никогда» (раздел 1).
- **Разбирается только ИДУЩИЙ эпизод.** Спецификация говорила «на закрытый», и это была
  ошибка: ожидание кончается ровно потому, что блокировку отпустили, и в `dm_tran_locks`
  её больше нет. Исправлено в коде и в [JOURNAL.md](JOURNAL.md).
- **Одна попытка на эпизод.** Пустая причина — отметка «ещё не пробовали»; заполненная
  причина закрывает вопрос. Без этого эпизод без документа разбирался бы заново каждый
  проход, и редкий разбор стал бы постоянным.

### Переходник проверяет себя сам

`Codeunit 110237` — **образец** подписчика, стоящий на штатной `Table 37 Sales Line`:
репозиторий публичный, номеров объектов заказчика в коде быть не может. На установке его
копируют и меняют три места.

Он проверяет себя сам и входит в общий прогон: пишет строку в таблицу контекста, смотрит,
легла ли отметка, и убирает за собой обе. Переходник, который ни разу не сработал, ничем
не отличается от отсутствующего.

По той же причине колонка «переходник заведён» заменена на **«отметки приходят»** — поле
смотрит, есть ли хоть одна отметка по этой таблице. Галка, поставленная рукой, врала бы
увереннее, чем пустое поле.

### Ловушки

- **Знак процента нельзя писать литералом** там, где текст потом попадёт в `STRSUBSTNO`:
  `%%lockres%%` прочтётся как подстановка. Псевдостолбец собирается из кода символа.
- **Удаление поля — разрушительное изменение схемы**, и компиляция таблицы отказывается
  его проводить: `The schema synchronization may result in deleted data`. На стенде
  разрешается ключом `SynchronizeSchemaChanges=Force`; в пакет для установки такой ключ
  не попадает — там удаление поля решение человека, а не скрипта.
- Имя колонки в журнале — `User Name`, а в отметке — `User Id`. Ошибка в имени колонки
  внутри склейки через `+` даёт не отказ, а **одну колонку вместо девятнадцати**: `NULL`
  съедает всю строку. Проверка на число колонок стоит одной строки и ловит это сразу.

## 18. Вторая дорога к документу: имя столбца не вычисляется, а спрашивается образцом

Дорога через отметку контекста требует переходника, а переходник — выкладки объекта.
Вторая дорога — обратный поиск по хэшу ключа в **самой спорной таблице** — не требует
ничего и работает с первого дня. Обе построены и проверены на живой блокировке
(`scripts/Test-Pass.ps1`, по двенадцать проверок на дорогу):

```
документ [HELD], откуда 1 (по хэшу блокировки)   -- дорога первая
документ [HELD], откуда 2 (по отметке контекста) -- дорога вторая
```

Значение у обеих здесь одно и то же нарочно: спорная строка в опыте и есть отметка
контекста. Различает дороги **источник**, и проверка ловит именно ту, которую включили.

**Порядок дорог изменён против исходного замысла**, и вот довод. Первая отвечает «за какой
документ идёт спор» — ровно тот вопрос, ради которого инструмент заводился. Вторая
отвечает «чем занят виновник». Поэтому первой идёт та, что про спор, а вторая подхватывает
там, где первая молчит: у страничной блокировки строки нет вовсе, а виновник, который
таблицу только читает, отметки не оставляет.

**По хэшу учётная запись не выдумывается.** Эта дорога отвечает про строку, а не про
человека, и `User Source` остаётся «нет» — проверено отдельно. Выдумать имя там, где его
никто не называл, журнал не вправе.

### Имя столбца: правило платформы не повторяется, а обходится

Перевод имени поля NAV в имя столбца SQL нигде не объявлен. Измерением видно, что точка и
косая черта становятся подчёркиванием (`No.` → `No_`, `G/L Entry` → `G_L Entry`), а
скобки, запятая, двоеточие, минус, плюс и амперсанд остаются как есть. Повторять чужое
правило по памяти — значит однажды промахнуться молча.

Поэтому имя переводится **не в имя, а в образец для `LIKE`**: всё, что не буква, не цифра
и не пробел, становится подчёркиванием, а подчёркивание в `LIKE` подходит к любому одному
знаку. Образец подходит и к замене, и к её отсутствию, и правило платформы знать не
требуется вовсе. Буква при этом определяется тем, что у неё различаются верхний и нижний
регистр — список диапазонов латиницы потерял бы кириллицу, а она в именах столбцов есть.

**Риск образца измерен, а не оценён на глаз.** Опасность одна: образец подойдёт к двум
столбцам сразу, и выбранный наугад даст правдоподобный, но чужой номер. На полной схеме
заказчика — **48 088 столбцов в 3 060 таблицах — столкновений НОЛЬ**. Съём всё равно
считает совпадения и при двух отвечает «не знаю»: ноль сегодня не обещает нуля завтра.

Само сравнение имени таблицы из SQL с именем объекта NAV идёт по тому же правилу и
проверено без базы: расхождение позволено только там, где в имени NAV стоит заменяемый
знак, поэтому `Gen_ Journal Line` — это `Gen. Journal Line`, но не `Gen. Journal Lint`.

### Цена

Чтение `dm_tran_locks` — по-прежнему **одно на проход**, и оно приносит блокировки для
обеих дорог сразу: и ту, за которую идёт спор, и ту, что держит отметку. Читать дважды
значило бы дважды заплатить за один скан.

## 19. Дорога к документу доведена до настоящей таблицы установки

07.09.2026, стенд 2 — полная схема заказчика. Проверялось не «работает ли обратный поиск»
(это было проверено раньше, раздел 17), а **доходит ли он до чужой таблицы, имена которой
инструмент видит впервые**. Прогон — `scripts/Test-Document.ps1`, одиннадцать проверок,
цель задаётся снаружи двумя числами: номер таблицы и номер поля.

Имена инструмент не получает и не угадывает — он их **спрашивает**: у NAV, по номерам
(`Record 2000000058` и `Record 2000000041`), и только потом переводит образцом в имена
SQL. В прогоне это отдельная проверка, и она первая: без имён остальные шли бы вхолостую.

| Что | Ответ |
|---|---|
| имя таблицы и поля по их номерам | NAV назвал оба |
| образец имени таблицы совпал в схеме | 1 раз |
| образец имени столбца совпал в таблице | 1 раз из 202 столбцов |
| номер документа в журнале | тот, что подложен |
| источник | 1 — по хэшу блокировки |
| учётная запись | пусто, источник 0 |

Ответ следует за данными, а не за кодом: второй опыт с другим номером даёт другой номер.

### Хэш спорной строки лежит у ЖЕРТВЫ, а не у виновника

Это исправление, а не подтверждение, и найдено оно измерением. Виновник держит столько
выданных блокировок, сколько строк тронул: держатель взял две строки — в `dm_tran_locks`
две записи `GRANT|U` на одном `hobt`, `(0e2051c31040)` и `(58bfd994691d)`. Прежний съём
брал хэш со стороны виновника и выбирал из них ПЕРВУЮ, а первой набор отдаёт ту, чей хэш
меньше. Для обычного случая «виновник обновляет пачку строк» это значит **чужой номер
документа, поданный уверенным тоном**, — худшее, что журнал вообще может сделать.

У жертвы на том же `hobt` запись ровно одна: `WAIT|U|(0e2051c31040)` — её собственная,
ещё не выполненная просьба, и она называет спорную строку однозначно. Отсюда правило:
`request_session_id` = сеанс жертвы, `request_status <> 'GRANT'`, тот же `hobt`.

Ждущая задача сама хэша не несёт вовсе. `dm_os_waiting_tasks` отдаёт
`keylock hobtid=… dbid=… id=lock1d800948100 mode=U`, где `id` — адрес объекта блокировки в
памяти, а не ключ строки. Спросить приходится именно `dm_tran_locks`, и это ничего не
стоит: чтение и так одно на проход, изменилось лишь условие отбора.

**Проверка на это заведена состязательной.** Виновник трогает две строки, спор идёт за
одну, а спорной прогон назначает ту, чей хэш БОЛЬШЕ, — тогда ответ «первая из тронутых»
заведомо указывает на другую. На прежнем коде опыт даёт {OLD}; на исправленном — 11 из 11.
Первый заход этой проверки, где роли назначались не по хэшу, прошёл на обоих кодах: без
состязательного выбора она была подбрасыванием монеты.

### Двое соврали по дороге, и оба — молча

- **`sqlcmd` без `-b` возвращает НОЛЬ и на ошибке SQL.** Вставка тестовой строки падала,
  проверка кода возврата этого не видела, опыт «блокировал» несуществующую строку, а
  красной оказывалась совсем другая проверка — «документ не назван». Инструмент при этом
  вёл себя правильно: строки нет, отвечать нечем, и он честно ответил «не знаю». Ключ
  `-b` поставлен во все прогоны сразу, а не только в тот, где поймали.
- **Умолчаний NAV в SQL не создаёт вовсе, а `NOT NULL` ставит везде**: в целевой таблице
  201 столбец из 202 без `DEFAULT`. Строку мимо NAV приходится собирать по списку
  `sys.columns` со значением по типу. И там же ловушка: у таблицы есть столбец `IDENTITY`
  (в этой базе они у 1 019 таблиц из 3 060), а вставка со списком всех столбцов падает на
  нём. В прогоне заведена и отдельная проверка «в первичном ключе цели нет автономера»:
  будь он там, подложенная строка адресовалась бы по значению, которое выбрал сервер, и
  опыт молча сменил бы цель.

### Исправление не стоило ничего

Условие отбора в том же единственном чтении `dm_tran_locks` поменялось, само чтение —
нет. Проход целиком перемерян под нагрузкой после правки: сотня настоящих ждущих,
**худший проход 384 мс при потолке 1000, установившийся 67 мс**, разовая надбавка первого
прохода 317 мс. Это не хуже замера до правки (раздел 16), то есть верный ответ обошёлся
даром.

Ещё одно место, где опыт был бы подлогом: `HOLDLOCK`. Он превращает блокировку в
диапазонную, а диапазонную берут на границе между строками — у неё нет строки вовсе, и
обратный поиск справедливо возвращает пустоту. NAV работает на уровне `read committed` и
диапазонных блокировок не берёт, поэтому и опыт их брать не вправе.

## 20. Взаимоблокировки: сервер их уже пишет, и теперь они в журнале

07.09.2026. Круг устраивается по-настоящему — подделать его нечем: два соединения берут
две строки в обратном порядке, сервер сам выбирает жертву и откатывает её. Прогон
`scripts/Test-Deadlock.ps1`, тринадцать проверок из тринадцати. Жертва назначается заранее ключом
`DEADLOCK_PRIORITY`: без него сервер выбирает по стоимости отката, и проверка «жертва та
самая» превратилась бы в угадывание.

Строка получается **того же вида, что обычный эпизод**: класс «взаимоблокировка», исход
«откат сервером», жертва и победитель, таблица `LockWatch Context Mark`, род `KEYLOCK`,
режимы `X` и `LCK_M_U`, длительность 4 251 мс, отпечаток графа. Колонка текста оператора
пуста — галка сбора значений выключена, и граф её не обходит.

### Где в графе лежит то, что нужно

| Что | Откуда |
|---|---|
| жертва | `victim-list/victimProcess/@id` |
| спорная строка | ресурс, в чьём `waiter-list` стоит жертва — **не любой из графа** |
| победитель | `owner-list/owner/@id` того же ресурса |
| таблица и индекс | `@objectname` вида `База.dbo.Компания$Таблица`, `@indexname` |
| номер сеанса, машина, процесс | `@spid`, `@hostname`, `@hostpid` у процесса |
| хэш спорной строки | `@waitresource` вида `KEY: 7:72057594815315968 (b07a8e60f8de)` |
| текст со значениями | `inputbuf` — только под галкой |

Ресурсов в графе столько, сколько сторон у круга, и взять «первый попавшийся» значит
назвать чужую таблицу — та же ошибка, что и с блокировками виновника в разделе 19.

### Пять мест, где это ломается молча

- **Время события в буфере — UTC, а всё остальное в том же графе местное.** Измерено на
  одном событии: `@timestamp="2026-09-07T19:50:24.284Z"` и рядом
  `lasttranstarted="2026-09-07T22:50:17.490"`. Сложить их — получить эпизод, начавшийся
  на три часа раньше собственной причины. Сдвиг берётся у самого сервера, разницей его же
  `GETUTCDATE()` и `GETDATE()`: считать её по часам NAV значило бы сложить две шкалы.
- **`Дата минус дата` в C/AL — не разница в днях.** Вторая дата берётся за ЧИСЛО ДНЕЙ, и
  проход падает с `The date is not valid`. Хуже всего, когда это падает: отметка
  «прочитано до» на первом проходе пуста, и первый проход отрабатывает начисто — отказ
  приходит только на ВТОРОМ. Компилятор молчит, первый прогон зелёный, ошибка ждёт до
  второй минуты работы. Считать разницу моментов: `At - CREATEDATETIME(Дата,0T)` даёт
  Duration, и она не врёт.
- **Пустая дата NAV в SQL — не NULL, а `1753-01-01`**, и столбец объявлен `NOT NULL`.
  Запрос, обнуляющий отметку через `NULL`, отвергается сервером.
- **Кольцевой буфер общий, и это ломает СОСЕДНИЕ прогоны.** В нём лежат чужие графы,
  записанные сервером когда угодно раньше, и проход законно вычитает их все. Измерено на
  себе: прогон по очереди, пущенный сразу после опытов со взаимоблокировками, дал **5 из
  12** — проход добавил двенадцать законных строк из буфера, и проверка «эпизод заведён
  ровно один» насчитала тринадцать. Отсюда два правила прогонов. Опыт со
  взаимоблокировками ставит отметку «прочитано до» на СЕЙЧАС и такой же её и оставляет:
  пустая отметка означает не «чисто», а «буфер не читан вовсе», то есть вычитать кольцо
  целиком. Опыты по очереди сбор взаимоблокировок на своё время выключают — две дороги
  проверяются порознь, и каждый прогон отвечает только за свою.
- **Тип `datetime` округляет отметку ВВЕРХ.** Шаг у него 3,33 мс, и отметка, собранная
  через него из суток и миллисекунд, оказывается на полтора миллисекунды позже настоящей.
  Событие ровно на границе при этом пропускается молча — то самое, ради чего отбор и сделан
  нестрогим. Найдено не рассуждением, а поломкой: со снятой проверкой отпечатка прогон
  обязан был покраснеть и не покраснел, потому что повтора просто не случилось. Собирать
  через `datetime2(3)`.

### Цена, и почему буфер читается не каждым проходом

Разбор буфера в XML стоит **около 150 мс на стороне сервера** (200 мс замером через
`sqlcmd` при его собственных 50 мс на запуск) — и это на буфере с единицами графов. Один
граф весит **13,6 КБ**, и большая его часть — `stackFrames`, адреса внутри модулей SQL
Server, не нужные никому.

Сто пятьдесят миллисекунд — это половина всей NAV-половины прохода и втрое дороже опроса
очереди в шторм. Поэтому буфер читается **не чаще раза в минуту**, а не каждым проходом:
он растёт не от наших блокировок, а от чужих взаимоблокировок, и на тихом сервере не
меняется вовсе. Верхнюю границу ставит оборот буфера — события старше вытесняются, — и
потеря при этом ЗАМЕТНА: проход сверяет старейшее событие в буфере со своей отметкой и
говорит об этом отдельной строкой.

Заодно: **`sqlcmd` работает с выключенным `QUOTED_IDENTIFIER`**, и любой метод XML в нём
отказывает — причём отказ называет не причину, а список требований к настройкам сеанса.
Драйвер `SqlClient` включает его сам, так что инструмента это не касается, а прогоны
включают явно. И в аргументе `-Q` нельзя двойных кавычек: разбор командной строки
рассыпается, а жалуется `sqlcmd` на «непредвиденный аргумент».

## 21. Советчик и сводка: ответ вместо данных, и порог, который наконец работает

07.09.2026. Журнал отвечал на вопрос «что случилось» и не отвечал на вопрос «что делать»,
а поле «порог тревоги» лежало в настройке и не участвовало ни в чём. Сделано и то, и
другое: **двадцать три** проверки в обкатке разбора и **семь** в мерном прогоне, и ни одна
из них не обращается к SQL.

### Совет — чистая функция, и потому проверяется без базы

Совет считается из того, что в строке эпизода УЖЕ есть: класс, исход, длительность, число
жертв за головой, признак агрегата SIFT, номер ключа, признак чужой головы. Ничего своего
советчик не добывает и никуда не ходит — значит, проверить его можно без единого ожидания
на стенде, и он проверен именно так.

Правил восемь, и порядок между ними важнее самих правил:

| # | Когда | Что сказать | Улика |
|---|---|---|---|
| 1 | класс «взаимоблокировка» | порядок захвата, а не индекс и не повтор | длительность |
| 2 | класс «эскалация» | размер пачки | длительность |
| 3 | класс «спит в транзакции» | звонок, а не правка кода | длительность |
| 4 | голова цепочки — не сессия NAV | разбираться на той стороне | длительность |
| 5 | спор за агрегат SIFT | ключ, а не индекс | номер ключа NAV |
| 6 | за головой две жертвы и больше | чинить голову, а не жертв | число жертв |
| 7 | исход «отказ по пределу» | смотреть, что держит так долго | длительность |
| 8 | длительность выше порога тревоги | смотреть операцию и документ | длительность и порог |

Порядок — **по тому, что делать**, а не по тому, как больно: беда, у которой есть своё
лечение, старше беды, про которую известна одна длительность. Сначала три класса, потом
три признака устройства, и только в конце длительность как таковая. Чужая голова стоит
выше агрегата и очереди нарочно: пока цепочку держит не сессия NAV, любой совет про ключи
и пачки адресован не туда.

**Улика рядом с советом обязательна.** Совет без числа, по которому он выдан, — это мнение:
его нечем оспорить и нечем проверить. Улика же ловит совет, выданный не по тому признаку, —
подпись при этом остаётся верной, и без числа подмена прошла бы молча.

**Ноль в пороге означает «не тревожить вовсе», а не «тревожить всегда».** Разница не
теоретическая: без этой оговорки выключенная тревога дала бы совет КАЖДОМУ эпизоду, и
советчик стал бы шумом, который перестают читать.

Порог «две жертвы за головой» — наименьший возможный: жертва за головой всегда есть хотя бы
одна, она сама, и порог в единицу означал бы «очередь есть всегда».

Из правил, намеченных в замысле ([JOURNAL.md](JOURNAL.md), раздел 13), не сделано одно —
«спор за конец индекса, все вставляют в одну страницу». Признака для него в строке нет:
отличить сквозной номер от прочих ключей можно, только зная устройство ключа, а не его
номер. Сделать вид, что признак есть, значило бы выдать догадку за улику.

### Сводка считается перебором, и это не лень

Сводка сводит журнал по паре «таблица NAV плюс ключ NAV» за окно и складывает: сколько
эпизодов, сколько из них выше порога, суммарное и самое долгое ожидание, когда был
последний. Строки упорядочены по СУММАРНОМУ ожиданию: число эпизодов говорит, как часто
задевали, сумма — во сколько это обошлось, и чинить начинают со второго.

Считается это ПЕРЕБОРОМ, а не агрегатом базы, и причина ровно та же, по которой в журнале
нет ни одного `SumIndexFields`: агрегат на таблице, куда фоновая задача пишет каждые три
секунды, сделал бы наблюдателя тем, за что дерутся. Сводку открывают руками и изредка, а
платить за неё пришлось бы каждой записью эпизода.

Совет в строке сводки — совет САМОГО ДОЛГОГО эпизода группы, а не самый частый: чинить
начинают с худшего, а частый совет на хвосте мелких ожиданий увёл бы в сторону. Сравнение
строгое, поэтому при равенстве побеждает первый встреченный, и строка не меняется от
порядка чтения.

Сумма объявлена `BigInteger` не для запаса: при сроке хранения в месяц двухсот тысяч
эпизодов по десять секунд хватает, чтобы перевалить предел `Integer`, и сумма молча ушла бы
в минус.

### Что проверено поломкой

Обе проверки непусты, и обе поломки сделаны нарочно.

**Поломка первая — три правила разом.** Очередь поставлена выше агрегата SIFT, улика SIFT
названа длительностью вместо номера ключа, и снята оговорка про нулевой порог. Обкатка
разбора дала **20 из 23** и покраснела ровно в трёх местах: агрегат получил совет очереди
(6 вместо 5), улика назвала `1000` вместо `3`, а нулевой порог выдал совет длинного
ожидания там, где тревога выключена. На целом коде — 23 из 23.

**Поломка вторая — порог сводки.** Счёт «выше порога» переведён на безусловный. Мерный
прогон дал **6 из 7**: проверка «порог и окно сводки настоящие» покраснела, а проверка
«сводка складывает числа» осталась зелёной — то есть краснеет именно то, что сломано.
На целом коде — 7 из 7.

Проверять порог одной сводкой бессмысленно: колонка «выше порога», равная числу эпизодов,
одинаково выглядит и у настоящего счёта, и у того, который порога не читает вовсе. Поэтому
порог в прогоне СДВИГАЮТ — одно и то же множество эпизодов сводится дважды, с порогом ниже
и выше их длительности, — а окно проверяется третьей сводкой, начинающейся позже последнего
эпизода.

### Цена

Советчик считается при КАЖДОЙ записи строки — на открытии, на обновлении и на закрытии, —
и такое решение стоило проверить числом. Замер сравнением, по два прогона на вариант:

| | без советчика | с советчиком |
|---|---|---|
| открытие 500 строк | 298 и 286 мс | 276 и 310 мс |
| обновление 500 строк | 194 и 185 мс | 190 и 206 мс |
| закрытие 500 строк | 71 и 60 мс | 60 и 69 мс |

Вывод отсюда не «советчик дёшев», а «советчик НЕ ВИДЕН»: разброс между двумя прогонами
ОДНОГО варианта (286 и 298) больше любой разницы между вариантами. Проход платит за запись
в SQL, а не за арифметику над полями строки, и восемь сравнений с парой `STRSUBSTNO` на этом
фоне не измеряются вовсе. Худший проход — 310 мс против объявленного потолка в 1000.

Это и есть довод считать совет ЗАНОВО при каждой записи, а не ставить один раз при открытии.
Совет обязан идти за строкой: ожидание растёт, класс меняется, исход появляется только в
конце, — и совет, поставленный при открытии, к закрытию был бы про другой эпизод. Платить
за это оказалось нечем.

## 22. Охват: сколько ожидания журнал вообще может назвать

08.09.2026. Сводка до сих пор молча обещала, что видно всё, — а это неверно и было неверно
с самого начала. Опрос очереди видит только те ожидания, которые дожили до следующего
прохода: ожидание в двести миллисекунд при периоде в три секунды не увидит никто, и таких
на живой базе большинство. Накопительный слой возвращается на своё настоящее место — не
сторожа (сторожем ему не быть, раздел 12), а ИТОГА, — и доля названного пишется на экран.

### Соединение с каталогом до отбора стоит в сто восемьдесят раз дороже

Запрос сперва был написан «как читается»: DMV, соединение с `sys.objects` и `sys.indexes`,
группировка, отбор. Замер — двадцать повторов на прогретом плане, стенд полной схемы:

| Что | Время |
|---|---|
| `SELECT COUNT(*)` по самому DMV (154 строки) | **0,37 мс** |
| группировка и отбор БЕЗ соединений | **0,41 мс** |
| соединение с каталогом ДО отбора | **82,70 мс** (худшее 95,70) |
| отбор в подзапросе, соединение ПОСЛЕ | **0,46 мс** (худшее 1,16) |

Сто восемьдесят раз на ровном месте. Причина в том, что у табличной функции нет статистики:
оптимизатор готовится к огромному набору и соединяет с каталогом из 13 838 объектов и 5 984
индексов ВСЁ, хотя после отбора остаются единицы строк. Сам он этого не исправляет —
исправлять надо руками, вынося отбор в подзапрос.

Это же и ответ на вопрос, почему слой читается КАЖДЫМ проходом, а не раз в минуту, как
кольцевой буфер взаимоблокировок: 0,46 мс дешевле опроса даже пустой очереди, и экономить
тут не на чем. Останься 82,7 — пришлось бы разносить чтение по времени, и охват отставал
бы от журнала.

### Что показывается и как это читать

Две пары чисел, и они не об одном и том же:

- **ожиданий против эпизодов** — сколько ожиданий было слишком коротким, чтобы их увидеть;
- **миллисекунд против миллисекунд** — сколько в этом было боли.

Обычная картина здоровой базы — «ожиданий видно десятую часть, а боли девять десятых»:
длинные ожидания опрос ловит почти все, а коротких много и они дёшевы. Поэтому доля
названного почти никогда не будет стопроцентной, и низкая доля сама по себе не поломка —
поломкой было бы её не знать.

Порог, ниже которого доля красится, — половина, и он не тот же, что порог тревоги: тот про
длительность одного эпизода, этот про то, можно ли вообще верить сводке как картине целого.

### Три места, где счёт врёт молча

- **Счётчик обнуляется.** Сервер обнуляет его, когда объект уходит из кэша метаданных, и
  видно это ровно одним признаком: значение стало МЕНЬШЕ прежнего. Разность была бы
  отрицательной, и итог поехал бы назад — правдоподобно и без единого сообщения. После
  обнуления за прирост берётся всё текущее значение, а сами обнуления считаются отдельным
  полем: случившееся перед самым обнулением потеряно, итог занижен, и молчать об этом
  нельзя.
- **Первое чтение индекса — только отметка, а не прирост.** Счётчик считает от неизвестного
  момента (когда объект попал в кэш сервера), и записать его целиком в «насчитано» значило
  бы приписать наблюдению всё, что случилось до его начала. Отсюда следствие, которое надо
  знать: на только что перезапущенном сервере первые проходы охват не наращивают вовсе.
- **Обе половины охвата считаются от ОДНОГО мига.** Отметка «охват считается с» ставится в
  тот же проход, что и первое чтение. Сравнить счётчики с этого мига с журналом за всё
  прошлое значило бы получить долю больше сотни процентов — и это лучший исход; худший в
  том, что доля была бы просто неверной, а выглядела бы правдоподобно.

### Что проверено поломкой

Обе поломки сделаны нарочно, и каждая ломает СВОЁ правило.

**Отсев обнуления снят** — `CounterDelta` перестал замечать, что счётчик пошёл назад.
Обкатка разбора дала **23 из 24**, и в красной строке видно ровно то, чего опасались:
прирост после обнуления **−993** вместо 7, то есть итог поехал назад.

**«Первое чтение — только отметка» снято** — накопитель стал считать приростом и самое
первое значение. Мерный прогон дал **7 из 9**: покраснели обе проверки накопителя, и это не
лишнее срабатывание, а следствие — обе меряют один и тот же итог, а сдвинулся он с первого
же чтения. На целом коде — 24 из 24 и 9 из 9.

Ломать пришлось порознь. Обкатка разбора идёт первой и при отказе останавливает прогон, так
что на сломанном разборе мерный прогон просто не запустился бы, и число «7 из 9» никто бы
не увидел. То же правило действовало и в разделе 21.

## 23. Переходник: цена подписки названа числом, а объект собирается, а не правится

08.09.2026, по разрешению заказчика. Переходник вешается на таблицу, куда пишут постоянно,
и вопрос «во что это обойдётся» решается числом. Числа три, и меньше нельзя: два без

| Вариант | Прогон 1 | Прогон 2 | Прогон 3 | Надбавка |
|---|---|---|---|---|
| подписчика нет вовсе (объект удалён из базы) | 434 | 427 | 420 мкс | — |
| подписчик есть, строка таблицы контекста выключена | 472 | 434 | 472 мкс | +2…12 % |

меньше, а не больше.

Три прогона приведены нарочно, а не усреднены. Из них видно, что честного вывода два, а не
один. **Цена РАБОТЫ подписки видна твёрдо**: отметка внутри транзакции пишущего стоит от
пятой части до трети цены записи, и в каждом прогоне включённый подписчик дороже
выключенного. **Цена самого ФАКТА подписки лежит на границе шума**: от двух процентов до
двенадцати при разбросе базового замера в те же три процента, и утверждать по этим числам
что-то определённее «немного, но не ноль» нельзя.

Отсюда и практический вывод: выключатель в строке настройки снимает большую часть надбавки,
но не всю — снять её целиком можно только снятием объекта.

**Замер на таблице заказчика намеренно НЕ делается.** На целевой таблице установки уже стоят
одиннадцать чужих подписок из семи кодюнитов, и вставка в неё меряла бы их работу, а не
нашу. Своя подписка стоит одинаково вне зависимости от того, сколько у неё соседей в списке.

### Первый прогон после перезапуска меряет не то

Тот же замер без разогрева дал **1043 мкс** на варианте «подписчика нет» — и вариант с
ВЫКЛЮЧЕННОЙ подпиской вышел быстрее (749 мкс), то есть замер противоречил физике. Причина:
после перезапуска служба собирает business assemblies и наполняет кэш метаданных, и это
больше половины первого замера. Первый прогон в каждом варианте теперь разогревочный, а
числом становится второй.

Ловушка тем и опасна, что молчит: числа выглядят настоящими, порядок правдоподобен ровно
настолько, чтобы его объяснить, и объяснение нашлось бы.

### Объект собирается подстановкой, а не правится руками

Номер таблицы у подписки — константа времени компиляции, поэтому на каждую таблицу контекста
нужен свой объект. Мест для правки **пять**: три подписки, тип записи в четырёх сигнатурах,
`DATABASE::` и имя поля. Промахнуться в них можно МОЛЧА — подписка на чужой номер таблицы
компилируется без единого замечания и просто никогда не срабатывает, а пустая колонка
документа читается как «спорили не за документы».

Поэтому объект собирает `scripts/New-ContextAdapter.ps1`, и каждая подстановка сверяется по
числу совпадений: образец правят, и правка, тихо разошедшаяся со сборщиком, дала бы объект,
который компилируется и не работает. Собранный объект кладётся в `out/` и в git не попадает:
номер таблицы заказчика — ровно то, чего в публичном репозитории быть не должно.

Проверено на настоящей таблице установки: объект собран, выложен, скомпилирован и сам себя
спросил у платформы — **3 из 3**. После проверки он со стенда снимается: оставлять
подписчика на чужой таблице прогон не вправе.

### Номера таблицы у подписки платформа не показывает

`Table 2000000140 «Event Subscription»` есть, и в ней видно всё, кроме главного: полей
1—4 и 6—13, а пятого — того самого, где был бы номер объекта-издателя, — **нет вовсе**
(измерено перебором `Table 2000000041 Field`). Спросить «подписан ли я на ТУ таблицу»
напрямую нельзя.

Отсюда две проверки вместо одной. Первая — что подписчик зарегистрирован и активен
(`Subscriber Codeunit ID` плюс `Active`). Вторая — **счётчик вызовов** `Number of Calls`:
ноль на живой таблице значит не «тихо», а «не туда». В образце к ним добавляется третья,
которой у собранного объекта быть не может: запись в таблицу и проверка, что отметка легла.
Вести её в чужой таблице нельзя — подложенная строка это документ из ниоткуда в учёте
заказчика.

### И ещё одна ловушка импорта

**Знак равенства внутри текста `TextConst` ломает импорт в C/SIDE.** Отказ указывает не на
причину: `'' is not an option. The existing options are:` и номер строки самой константы.
Разбор языковых кусков (`ENU=…;RUS=…`) спотыкается о лишний `=` в значении. Машиночитаемый
ответ мерного объекта пришлось писать через пробел: `ms %1 rows %2`, а не `ms=%1`.

## 24. Тревога: порог наконец зовёт человека, и зовёт его один раз

08.09.2026, по разрешению заказчика. Порог тревоги до сих пор делал две вещи — красил
строку и давал восьмое правило советчику, — но человека не звал никто. Теперь зовёт, и
главный вопрос тут не «как позвать», а «как не превратить это в шум, который перестают
читать».

### Защёлка по голове цепочки, а не по эпизоду

Одна забытая транзакция в шторм держит сотни жертв. Тревога на каждую — это сотня строк, и
через день их перестают открывать; в тот раз, когда тревога была нужна, она не сработает
именно поэтому. Поэтому строка — на ГОЛОВУ цепочки за окно в пять минут, а число эпизодов
за защёлкой растёт полем и само по себе есть мера того, скольких задело.

Тревога поднимается только на ИДУЩИЙ эпизод. Смысл её — «происходит сейчас, вмешайся»;
звать человека к тому, что кончилось само, значит приучить его не читать. Взаимоблокировки
сюда по той же причине не попадают: круг разорвал сервер, звать за этим некого.

### Канал наружу — журнал событий Windows, и это не от бедности

Своего канала в журнал событий у C/AL 2018 нет вовсе; почта требует настроенного SMTP,
которого может не быть; а журнал событий Windows — ровно то, что мониторинг на сервере и
без нас уже читает. Пишем через штатную `System.Diagnostics.EventLog` — сборка платформы,
никаких `Add-ins`, как и с `System.Data`.

Источник событий заводит администратор один раз на машину
(`New-EventLog -LogName Application -Source LockWatch`). Создавать его из кода мы не
пробуем вовсе: создание требует прав, которых у службы нет и быть не должно, а неудачная
попытка выглядит в журнале приложений отказом безопасности — шумом, за который отвечать
нам. Писать в ЧУЖОЙ источник — скажем, в источник самой службы NAV — тоже нельзя:
мониторинг припишет запись платформе, и разбираться будут не с тем.

Пока источника нет, канал молчит — но молчит СЛОВАМИ: причина пишется в саму строку
тревоги, рядом с колонкой «куда ушла». Молчащий канал, о котором никто не знает, хуже
отсутствующего.

### Что проверено поломкой

Три поломки, и каждая красит своё:

| Что сломано | Прогон | Результат |
|---|---|---|
| снято окно защёлки | мерный | **10 из 11**, краснеет только проверка окна |
| снята сама защёлка | мерный | **9 из 11**, краснеют обе проверки тревоги |
| снят канал наружу | по живой блокировке | **14 из 15**, краснеет только «ушла наружу» |

На целом коде — 11 из 11 и 15 из 15. Первая поломка тем и ценна, что оставила первую
проверку зелёной: защёлка внутри окна работала, а окно не кончалось никогда — и без
отдельной проверки на состаренной тревоге это выглядело бы в точности как исправный код.

Канал наружу — единственная часть тревоги, которую нельзя проверить изнутри NAV: запись в
журнале событий Windows либо есть, либо её нет, и спросить об этом можно только сам журнал.
Прогон и спрашивает — `Get-WinEvent` по источнику и времени начала опыта.

### Собранный объект чуть не съел свой же инструмент

Прогон переходника собирал объект под номером 110240 — и ровно этот номер к тому времени
занял кодюнит тревоги. Импорт собранного объекта перекрыл его молча, а уборка прогона потом
удалила, и отказ вылез **через два прогона** и в другом месте: сторож не проснулся, а
нагрузочный прогон сказал «объект 110240 не найден».

Отсюда правило и сторож при нём: собственный диапазон инструмента — 110230..110249, и
сборщик отказывается собирать объект внутри него. Номер объекта — это имя, и занять чужое
имя молча так же легко, как подписаться на чужую таблицу.

### И третий раз одна и та же ловушка

**Точка с запятой и знак равенства внутри многоязычного текста ломают импорт в C/SIDE.**
Отказ указывает не на причину: `'' is not an option. The existing options are:` либо
`You cannot enter ... in ToolTipML`, и номер строки. За сессию это стоило трёх прогонов,
поэтому проверка теперь стоит в выкладке ДО `finsql`: содержимое каждого `…ML=[…]` и
каждого `TextConst '…'` разбирается, и всякая точка с запятой обязана быть разделителем
языков, а знаков равенства должно быть ровно столько, сколько языков.

## 25. Врезка в меню: своего уровня не дали, и объект приходится сливать

08.09.2026, по разрешению заказчика. Страницы до сих пор открывались только запуском
объекта, а поиск по меню их не находил вовсе. Оказалось, что дело не в лени, а в лицензии.

### Партнёрских уровней MenuSuite лицензия не даёт ни одного

Проверено перебором: минимальный `MenuSuite` заводился под номерами **1020, 1040, 1050,
1060, 1070 и 1080**, и на каждом получен один и тот же отказ —
`You do not have permission to create the ... MenuSuite`. Остаётся уровень Company (1090),
а он на установке уже есть и принадлежит заказчику.

Значит, свой объект выложить нельзя, и пункты приходится ВРЕЗАТЬ в чужой.

### Company-уровень — надстройка, а не дерево

Первая попытка врезки уткнулась в то, что в выгруженном `MenuSuite 1090` **нет узла
`Root`**: 667 узлов, из них 4 меню, 77 групп и 503 пункта, и ни одного корня. Причина в
устройстве: уровень Company — НАДСТРОЙКА над нижними уровнями, в ней лежит только
изменённое и добавленное, а `Root` живёт на уровне MBS.

Отсюда способ поиска места врезки: не обход от корня, а признак «меню верхнего уровня, за
которым никого нет». Такое в объекте должно быть ровно одно; если их два или ни одного,
скрипт отказывается работать, а не угадывает.

### Правится ровно один чужой узел

Слияние меняет **одну строку** в чужом объекте — `NextNodeID` последнего меню, — и
дописывает 77 строк своих. Меньше одного узла не выходит: цепочка меню односвязная, и
попасть в неё можно только через предыдущее звено.

Слияние идемпотентно: свои узлы сначала убираются вместе со ссылкой на них, потом
дописываются заново. GUID узлов постоянны нарочно — смена их дала бы второй комплект
пунктов рядом с первым, и убрать его можно было бы только руками.

Импорт слитого объекта скрипт сам не делает: это правка чужого объекта, и решение о ней
отдельное, ключом `-Import`.

### Что проверено поломкой, и почему две поломки из трёх не покраснели

Прогон `scripts/Test-Menu.ps1`, четыре проверки из четырёх, и главная из них — не «видно
ли пункты» (клиента прогон не открывает), а **обратимость**: объект сливается,
выкладывается, сливается повторно и разбирается обратно, и обязан совпасть с исходным
БАЙТ В БАЙТ.

| Что сломано | Результат |
|---|---|
| снята идемпотентность (прежняя врезка не убирается) | скрипт ОТКАЗАЛСЯ: «меню без продолжения оказалось 2» |
| снят возврат ссылки при снятии врезки вообще | скрипт ОТКАЗАЛСЯ: «меню без продолжения не нашлось» |
| возврат ссылки снят ТОЛЬКО в режиме снятия | **3 из 4**, краснеет проверка обратимости |

Две поломки из трёх не покрасили проверку, а упёрлись в сторож самого слияния — и для
скрипта, который правит чужой объект, это лучший из возможных исходов: он не сделал
неверную правку, а отказался её делать. Третья поломка сделана отдельно именно затем,
чтобы проверка обратимости доказала свою непустоту красным.

### Восстанавливаться надо не той логикой, которая сломалась

Первый заход поломки оставил чужой объект в состоянии, которое сам скрипт потом отказался
трогать: ссылка ведёт на узел, которого больше нет. Вернуть его было нечем — снятие врезки
шло тем же кодом, который и сломали.

Поэтому прогон возвращает объект **импортом сохранённой выгрузки**, а не снятием врезки:
файл оригинала от логики слияния не зависит вовсе. Правило общее и не про меню: откат,
идущий через тот же код, что и правка, — это не откат.

## 26. Имена людей от платформы: ключ взвели, и он ничего не купил

08.09.2026, по разрешению заказчика. Это был последний вопрос из списка и единственный,
ради которого предлагалось платить конфигом, перезапуском, обоими правами SQL и постоянной
серверной сессией XE. Ответ измерен, и он отрицательный.

### Замер

Ключ `EnableDeadlockMonitoring` взведён, экземпляр перезапущен. Проверено инструментом:
оба права у учётной записи службы на месте, серверная сессия мониторинга **поднята
платформой** — то есть код `SetupDeadlockAnalyzer` отработал. Дальше сессия NAV берёт
блокировку на строку, вторая сессия встаёт в очередь за ней, и штатная
`Table 2000000154 «Database Locks»` отдаёт:

| Кто читает | Строк |
|---|---|
| сторонний наблюдатель при живой блокировке и непустой очереди | **0** |
| САМ ДЕРЖАТЕЛЬ, изнутри собственной открытой транзакции, сразу после взятия | **0** |
| он же, полминуты спустя, когда ждущий уже стоит в очереди | **0** |

Карта транзакций не наполняется вовсе. Держатель не видит даже СВОЕЙ блокировки — а это
единственный случай, в котором никакие оговорки провайдера (чужая компания, чужой
экземпляр, чужое соединение) роли не играют.

**Вывод: включать `EnableDeadlockMonitoring` не за чем.** Цена его расписана в разделе 2 и
не нулевая — а покупает она, по этому замеру, ноль.

### Оговорка, без которой вывод был бы шире измеренного

Обе читающие стороны — сессии, поднятые `Invoke-NAVCodeunit`, то есть клиент типа
Management. Сессия обычного клиента Windows не проверялась: клиент прогон не открывает.
Утверждать, что таблица пуста и для неё, оснований нет — и потому здесь этого не сказано.

### Что из этого всё же сделано

Дорога оставлена в коде, и не из упрямства: сборки платформы разные, а сторож при ней
говорит правду в любом случае. Сторож этот и есть главное, потому что **отказ дороги
невидим**: не выдали право или не наполнилась карта — таблица ведёт себя в точности как при
отсутствии блокировок, и экран одинаково пуст на здоровой системе и на сломанной.

Поэтому проверок в стороже три, и последняя из них решающая:

1. оба права SQL — тем же запросом `HAS_PERMS_BY_NAME`, каким проверяет сама платформа;
2. серверная сессия мониторинга — работает ли она на самом деле;
3. **перекрёстная**: в очереди сервера есть ожидания блокировок, а штатная таблица пуста —
   значит карта мертва. Без этой проверки инструмент сказал бы «всё хорошо» и показал
   пустую колонку.

И второе правило, столь же важное: **имя, которого платформа не дала, не выдумывается**.
Источник имени остаётся тем, что назвала наша собственная отметка контекста, а причина
молчания пишется словами.

Колонка `AL Method Scope` подписана честно — «где виновник исполняется СЕЙЧАС», а не «где
взял блокировку»: платформа берёт её из живого стека в момент чтения, и два соседних чтения
одного эпизода назовут разные объекты (раздел 2).

### Две ловушки прогона, и обе про сам опыт

- **Опрос «взял ли держатель блокировку» встал в очередь за этой самой блокировкой.**
  Обычное чтение той же строки блокируется, возвращает ответ уже ПОСЛЕ конца удержания, и
  ждущему не за чем вставать: `sqlcmd` умирал сразу с нулевым кодом, а выглядело это как
  «инструмент не увидел блокировку». Опрос обязан читать ГРЯЗНО.
- **Ждущий, умерший на старте, неотличим от ждущего, который не успел встать в очередь.**
  Разница видна только по самому процессу, и спрашивать о ней надо ДО того, как прогон
  объявит инструмент виноватым.

### Что проверено поломкой

Обе проверки, ради которых дорога и оставлена в коде, ломались отдельно, и каждая покраснела
ровно одна:

| Что сломано | Результат |
|---|---|
| снята перекрёстная проверка (пустая таблица при непустой очереди) | **4 из 5**, краснеет «карта мертва» |
| снят отказ выдумывать имя (строка не нашлась, а имя пишется) | **4 из 5**, краснеет «имя не выдумано» |

На целом коде — 5 из 5. Первая поломка тем и опасна, что делает инструмент ВЕЖЛИВЫМ: он
говорит «дорога жива», показывает пустую колонку, и читается это как «спорили без людей».
Вторая — что делает его УБЕДИТЕЛЬНЫМ: имя появляется, источник у него платформенный, и
оспорить его нечем.

## 27. Смета: двенадцать прогонов стали одним, и судья к ним проверен поломкой

08.09.2026. Прогонов к этому дню набралось одиннадцать, и порядок их вместе с
предусловиями жил в голове того, кто их писал. Это первый вид знания, который теряется, а
потеря его дорога особым образом: **прогоны мешают друг другу не отказом, а зелёным
цветом**.

### Почему порядок, а не список

Кольцевой буфер сервера один на всех. Взаимоблокировки, устроенные одним прогоном,
попадают в журнал следующего; проход по очереди находит эпизоды, которых сам не
устраивал, и краснеет проверка, к которой это не имеет отношения. Ловилось на себе:
проверка прохода дала 5 из 12, и виноват был не проход.

Поэтому у каждого места в очереди записан довод:

| Место | Прогон | Довод |
|---|---|---|
| 1 | выкладка | всё дальнейшее меряет то, что она положила на стенд |
| 2–3 | проход, обе дороги | кратчайший путь до живого эпизода: сломан он — дальше всё шум |
| 4 | документ | дорога доводится до чужой таблицы после того, как проверена на своей |
| 5 | взаимоблокировки | оставляют настоящие круги в буфере: только после прогонов по очереди |
| 6 | сторож | ему нужен спокойный журнал: он судит по тому, что появилось САМО |
| 7 | нагрузка | сотня ждущих греет сервер; раньше сторожа нельзя |
| 8 | переходник | снимает со стенда штатный переходник; кому он нужен целым, уже прошли |
| 9 | меню | единственный, кто пишет в объект установки |
| 10 | платформа | дважды перезапускает экземпляр: следующий вход платит за business assemblies |
| 11 | снятие | снимает всё: после него мерить нечего, пока не выложишь заново |
| 12 | повторная выкладка | возвращает стенд в рабочее состояние — и это второй замер: выкладка на ОЧИЩЕННУЮ базу |

### Ведомость: почему нельзя верить нулевому коду возврата

Прогон, молча выполнивший три проверки вместо пятнадцати, выходит с нулевым кодом и был
бы засчитан зелёным: отказа не было, отчёт есть, число в нём **сходится само с собой**.
Поэтому у каждого прогона записано, сколько проверок он делал, когда его писали. Меньше —
красный цвет; больше — повод обновить ведомость, а не молчаливое согласие.

Невыполненное считается **отдельно** и со сделанным не складывается: прогон, который
нельзя выполнить, — не утверждение, и в сумму утверждений он не идёт.

### Что судья говорит на подставного

Судью нельзя проверить теми же прогонами, которые он судит: они зелёные, и молчание его
неотличимо от согласия. Поэтому на его место подставлялся заведомо известный ответ.

| Подопытный сказал | Код возврата | Что сказала смета |
|---|---|---|
| «пройдено 5 из 5» | 0 | зелёный — судья не залип на красном |
| «пройдено 3 из 3» | 0 | **ПРОВАЛ**: проверок 3 вместо 5, часть их молча не выполнилась |
| про итог ничего | 0 | **ПРОВАЛ**: в отчёте нет ни одной строки итога |
| «пройдено 2 из 5» | 0 | **ПРОВАЛ**: в отчёте есть непройденное |
| «пройдено 2 из 5» | 1 | **ПРОВАЛ**: код возврата 1 |

Шестым проверено предусловие: прогон дороги к документу без заданной целевой таблицы
попадает не в «пройдено» и не в «провалено», а в отдельный список невыполненного — и
смета всё равно отказывает.

Второй строкой этой таблицы держится вся ведомость, четвёртой — недоверие к коду
возврата, третьей — случай, когда прогон перестал отчитываться вовсе.

### Цена

Служба поднимается **один раз на всю смету**, и дочерним прогонам ключ остановки не
передаётся никогда: погасивший её посередине заставил бы следующего заплатить холодным
стартом, и замер цены прохода стал бы замером разогрева.

| Прогон | Проверок | Время |
|---|---|---|
| выкладка и обкатка | 37 | 22 с |
| проход по очереди | 18 | 12 с |
| проход по отметке | 18 | 11 с |
| документ | 11 | 24 с |
| взаимоблокировки | 13 | 1,7 мин |
| сторож | 7 | 41 с |
| нагрузка | 6 | 8 с |
| переходник | 8 | 1,6 мин |
| меню | 4 | 9 с |
| платформа | 5 | 84 с |
| снятие | 5 | 2 с |
| повторная выкладка | 37 | 18 с |
| **всего** | **169** | **7,2 мин** |

### Что смета нашла на первом же полном заходе

Она покраснела — и не на инструменте. Прогон взаимоблокировок отказал с «граф в буфер не
попал» там, где двумя заходами раньше выходило 13 из 13.

Круг между двумя соединениями — опыт **вероятностный**, и это его свойство, а не
недоделка: обе стороны обязаны взять свою первую блокировку прежде, чем первая пойдёт за
второй. На занятой машине одна запоздала со стартом дольше пятисекундной паузы, и круга не
вышло вовсе — оба соединения отработали по очереди и вышли с нулём.

В ручном прогоне такое списывают на невезение и забывают. Смета со случайным цветом хуже
отсутствующей: её перестают читать.

Починено двумя вещами разом — пауза удвоена до десяти секунд, попыток три вместо одной, и
каждая неудавшаяся называется вслух. Проверено поломкой: обе стороны направлены на строки
**в одном порядке**, круг тогда невозможен в принципе, и прогон даёт три названные попытки
и отказ по существу. На исправленном коде — 13 из 13, оба круга с первой попытки.

Отказ при этом **не оборвал смету**: остальные одиннадцать прогонов отработали и дали свои
числа. Ради этого правило и заведено — иначе на каждую поломку уходил бы день.

Один отказ смету не обрывает: остальные прогоны идут, иначе на каждую поломку уходил бы
день — по одному красному за заход. Исключение единственное и с доводом: если не встала
выкладка, всё дальнейшее меряет вчерашние объекты, и зелёный цвет там хуже красного.

## 28. Снятие: что остаётся после инструмента, и почему «ничего не осталось» — проверка пустая

08.09.2026. Спрашивают обычно не «что он делает», а «что после него останется», и до этого
дня ответа не было вовсе: снять инструмент было нечем. Теперь снятие — не список действий,
а прогон, который убирает, а потом сверяет по базе, что убралось, и судит себя сам.

### След, измеренный

| Что | Сколько | Где |
|---|---|---|
| строк в `Object` | **33** | 7 данных таблиц, 7 таблиц, 13 кодюнитов, 6 страниц |
| таблиц SQL | **7** | вместе с ними уходят данные: журнал, тревоги, охват, настройка |
| строк планировщика | 0–1 | таблица общая на базу, живёт вне компании |
| врезка в чужом `MenuSuite` | одна изменённая строка | снимается отдельно, возвращает объект байт в байт (раздел 25) |
| собранный переходник | один объект | **вне** объявленного диапазона: номер ему выбирают под установку |
| источник событий Windows | один | в реестре машины, не в базе |
| серверная сессия XE | 0–1 | только если ключ мониторинга когда-нибудь включали (раздел 2) |

Тридцать три строки на двадцать шесть объектов — не описка: у таблицы в `Object` **две**
строки, сам объект и отдельно её данные. Сложить их и назвать сумму «объектами» значит
соврать в описи, а читают её именно как опись.

### Порядок и его доводы

**Сторож снимается первым**, и довод к этому был рассуждением, пока его не измерили —
замер рассуждение поправил. Строка задачи переживает удаление своего кодюнита. Проснувшись
в пустоту, задача кладёт в журнал событий Windows **ошибку** с трассировкой стека:

```
Category: TaskScheduling
Message (NavNCLMetadataObjectNotFoundException): Object of type CodeUnit with ID … could not be found.
```

…после чего платформа **убирает строку сама**: через сорок секунд в таблице ноль. Значит
бесконечного повторения нет, и это лучше, чем ожидалось. Но ошибка появляется на пустом
месте и уже после того, как инструмент сняли, — а разбирать её будет тот, у кого его
больше нет.

Дальше: **врезка в меню — до удаления страниц** (иначе есть окно, где чужое меню ссылается
на объекты, которых уже нет); **собранный переходник — раньше прочих объектов** (он
единственный исполняется на чужой записи); **свои объекты — в обратном порядке сборки**:
страницы, кодюниты, таблицы.

Вердикт снимается **из базы, а не из лога finsql**: удаление несуществующего объекта — не
отказ, а пустое место, и различать эти два случая по тексту в логе значит гадать.

### Почему «ничего не осталось» само по себе ничего не значит

Проверки «объектов нет», «таблиц нет», «задач нет» проходят на базе, где инструмент **не
стоял никогда**: ноль там и до снятия, и после. Прогон, объявляющий на такой базе
«снято», доказывает не снятие, а собственную бесполезность.

Проверено поломкой: снятие, запущенное второй раз подряд по уже чистой базе, даёт

| Проверок | Что покраснело |
|---|---|
| **3 из 3** без проверки разницы | ничего — снятие объявлено состоявшимся |
| **3 из 4** с ней | «до снятия было что снимать»: объектов 0, таблиц 0 |

Поэтому первой мерится не пустота, а **разница**, и опись «до» печатается в отчёт.

### Забытый номер переходника

Собранный переходник ставится **вне** объявленного диапазона — номер ему выбирают под
установку. Забытый при снятии, он остаётся подписан на чужую таблицу, потребителя у
которой уже нет. Ищется он по имени: сборщик зовёт его `LockWatch Adapter <номер таблицы>`,
и это единственный след, не зависящий от того, вспомнил ли человек номер.

Найдя такой объект, прогон **называет его и отказывается признать снятие полным**, но сам
не трогает: удалять объект, которого никто не называл, он не вправе. Решение остаётся за
человеком, а молчаливого «всё чисто» при живой подписке не бывает.

Имя источника событий по той же причине читается из настройки **до** удаления таблиц:
после спросить будет не у кого, а выбирает его установка, а не мы.

### Установка на очищенную базу

Снятое ставится обратно: выкладка → снятие → выкладка, обкатка по 37 проверок в обоих
заходах. Это не повторение, а второй замер — выкладка на базу, с которой инструмент только
что сняли, начинается из другого состояния, чем выкладка поверх стоящего.

### Чего снять оттуда нельзя

- **Источник событий Windows** — в реестре машины. Снимает администратор:
  `Remove-EventLog -Source <имя из настройки>`.
- **Серверная сессия Extended Events**, если ключ мониторинга включали, — переживает
  снятие инструмента и уходит только обратным выключением ключа и перезапуском экземпляра
  (раздел 2). Ключ включать не за чем (раздел 26), но если его включали — это остаётся.

Оба перечисляются отдельным списком и со снятым не смешиваются никогда.

### Обе ветви, которых смета не берёт, — и что нашлось, когда их прошли

К концу сметы на стенде нет ни врезки в меню, ни собранного переходника: их убирают
собственные прогоны. Поэтому две ветви снятия оставались непройденными, и это было
записано. Пройдены они 08.09.2026, поставив оба следа на стенд нарочно, — и обе нашли по
делу.

**Ветвь меню была сломана, и сломана так, что покраснела бы всегда.** Сверка искала GUID
нашего меню в выгрузке чужого объекта, а брала его наивным `ID=[{…}]` — образец цепляется
и к `ParentNodeID=`, и к `NextNodeID=`, и первым в заготовке стоит **нулевой** GUID. Он
есть в любом чужом `MenuSuite`, поэтому «врезка стоит» отвечалось и на снятой врезке. Со
стороны это выглядело как отказ снятия, а сломана была сама сверка.

Исправлено разбором из заголовка записи узла — тем же, каким пользуется слияние, — и
ищутся теперь **все восемь** наших узлов, а не одно меню: врезка, снятая наполовину,
оставила бы пункты без меню, и проверка по одному меню назвала бы это чистотой. На стоящей
врезке счёт даёт 8 из 8, на снятой 0 из 8; проверка мерит разницу, а не пустоту.

**Снятие со всеми следами разом — 7 из 7.** Опись при этом называет собранный переходник
типом, номером и именем, а если его номер не назван ключом — отказывается признать снятие
полным. Проверено поломкой: снятие, запущенное «забыв» номер, даёт 4 из 6 и краснеет
именно там, где переходник остался жив.

### Снять при остановленной службе нельзя, и полдела хуже отказа

Второй непройденной ветвью было снятие с погашенным экземпляром. Ответ измерен, и он
отрицательный: **таблицы без службы не снимаются**. Схему SQL меняет она, и `finsql` без
её координат отвечает

```
Unable to process table changes because the Microsoft Dynamics NAV Development
Environment cannot connect to the specified Microsoft Dynamics NAV Server instance:
… Management Port: 0
```

Хуже, чем просто отказ: страницы и кодюниты при этом **уходят**, а семь таблиц с данными
остаются. Снятие делает полдела и оставляет базу с таблицами без кода — 2 из 5 по сверке,
и разбирать это человеку.

Поэтому проверка стоит теперь **до первого удаления**, а не разбор последствий после
него: без запущенного экземпляра прогон отказывается работать вовсе и говорит, чего ему
не хватает. Проверено: при погашенной службе строк в `Object` до вызова 14 и после вызова
14 — не тронуто ничего. Опись следа при этом читается и без службы, потому что она чистое
чтение SQL.

Половинное снятие, если оно всё-таки случилось, **лечится выкладкой**: объекты встают
поверх осиротевших таблиц SQL, и обкатка проходит целиком.

## 29. Текст запроса в журнале: не «что заблокировано», а «чем занимались»

08.09.2026, по просьбе. Журнал называл таблицу, ключ, документ и учётную запись — но не
называл САМУ ОПЕРАЦИЮ. Короткое поле на 250 знаков заполнялось только на взаимоблокировках,
а по очереди сервера текста не снималось вовсе.

Теперь оператор лежит в журнале целиком, полем-БЛОБом, и открывается кнопкой.

### Что и откуда берётся

| Чей | Откуда | Что приходит |
|---|---|---|
| жертвы | `dm_exec_requests` + `dm_exec_sql_text`, по точным границам оператора | **параметризованный** запрос из кэша планов: `set [Document No_] = @1` |
| виновника | `dm_exec_connections.most_recent_sql_handle` + `dm_exec_sql_text` | **сырой батч** его соединения, со всеми литералами |
| виновника при взаимоблокировке | `inputbuf` из графа `system_health` | входной буфер, который сервер сам обрезает на 4000 знаках |

**Разница между первыми двумя — не мелочь, а свойство дороги.** Жертва ждёт, то есть у неё
есть исполняемый запрос, и текст его берётся из кэша планов — значений там нет. Виновник
чаще СПИТ (в этом вся беда блокировок NAV), исполняемого запроса у него нет, и берётся
последний, что он послал: тот самый оператор, который взял блокировку, — с литералами.

Из этого следует и правило проверки: искать в запросе жертвы значение, которое туда клали,
бессмысленно — его там не будет никогда.

### Цена и выключатель

Текст стоит **четырёх присоединений** к горячему запросу прохода, и потому он выключаем —
тем же признаком «Собирать значения в операторах», который и так решал вопрос о значениях.
Выключенный не платит ничем: колонки остаются на месте пустыми, а присоединений в запросе
нет вовсе.

Потолок — 16 000 знаков, с отметкой усечения **внутри самого текста** и комментарием SQL,
чтобы скопированный в studio запрос не сломался. Довод к потолку не про экран, а про базу:
текст пишется на каждый ОТКРЫТЫЙ эпизод, а в шторм их сотня за проход.

Пишется он **один раз, при открытии**, и дальше не трогается. Довод не в экономии: строка
обновляется каждым проходом, и переписывать текст заново значило бы менять его под
читателем — виновник за три секунды успевает послать другой оператор, и в журнале оказался
бы не тот, который взял блокировку.

Блоб хранится **несжатым**, и это решение. Сжатый читается только через NAV: ни прогон, ни
администратор базы не достанут из него ни строчки, и проверка, которая не может прочитать
то, что проверяет, доказывает лишь наличие байтов.

### Пять ловушек, и каждая молчит по-своему

- **`LEN()` на `nvarchar(max)` возвращает `bigint`.** `GetInt32` падает с «Specified cast is
  not valid» — на первой же строке очереди, то есть ровно тогда, когда блокировка наконец
  случилась. Та же семья, что и `smallint` у номера сеанса: приводить к `int` явно.
- **`CAST(image AS varchar(max))` сервер не разрешает вовсе.** Только через
  `varbinary(max)`. Ловится не в коде, а в проверке, которая этот блоб читает.
- **Поток в блоб открывается ДО `INSERT`, а не после.** Написанное после вставки и
  закреплённое `MODIFY` до читателя не доезжает: обычные поля доехали, блоб пуст. Выглядит
  как «текст не сняли», хотя сняли и потеряли.
- **`CALCFIELDS` обязателен ДАЖЕ на временной записи** — ровно наоборот тому, чего ждёшь: у
  временной таблицы значения и так в памяти. Без него `HASVALUE` отвечает «нет» при
  полностью заполненном источнике, и перенос молча не происходит.
- **`.value()` не принимает `nvarchar(max)`.** Для графа взаимоблокировки берётся
  `nvarchar(4000)`, и это ничего не теряет: сервер сам обрезает входной буфер там же.

### Что нашлось по дороге, и это дороже самой работы

Считая колонки для новых полей, обнаружилось, что **съём очереди читал их на единицу
раньше**. Начало транзакции виновника собиралось из признака «у виновника есть исполняемый
запрос» и номера дня: в журнале стояло **`1900-01-02 00:00:46`**. А класс эпизода считался
по миллисекундам вместо признака.

Обе величины целые, обе правдоподобные, отказа нет — **ни одна из ста шестидесяти трёх
проверок этого не ловила**. Исправлено, и проверено значением: `2026-09-08 12:26:01`
вместо `1900-01-02`.

### Проверено поломкой

Колонки жертвы и виновника поменяны местами — самая дорогая из возможных ошибок здесь:
чужой запрос выглядит ровно так же убедительно, как свой. Прогон даёт **16 из 18** и
краснеет обеими проверками разом, печатая саму подмену: в поле жертвы 167 байт с `WAITFOR`,
в поле виновника 90 без `HELD`. На исправленном коде — 18 из 18 на обеих дорогах.

Состязательность держится на том, что стороны говорят РАЗНОЕ: виновник пишет в строку
`HELD` и держит `WAITFOR`, жертва пишет `WANT` и не держит ничего. Проверка «текст непустой»
прошла бы и на тексте не того сеанса.

## Что осталось непроверенным

- Разные пользователи NAV на стенде недоступны: локально одна учётная запись, обе сессии
  опыта шли под одним именем. «Покажет ли платформа два РАЗНЫХ имени» — за целевым контуром.
- Непустую `Table 2000000154` не видел никто: весь режим с именами — вывод из декомпиляции.
- Базовое число ждущих задач на боевом сервере в час пик. Если там сотни — фоновый опрос
  очереди не годится в принципе.
- Насколько часто блокировка садится именно на SIFT: на стенде из 308 представлений
  заполнено одно, объёмов нет.
- Роль службы в базе на целевом контуре (на стенде `db_owner`).
- Снятие с установки, где ключ `EnableDeadlockMonitoring` был включён: серверная сессия XE
  переживает снятие (раздел 2), и убрать её нечем, кроме обратной правки конфига. На
  стенде ключ выключен, и этот случай не гонялся.
